# Version log: v0.23.2-dev – v0.23.20-dev

Original order is newest first, as it was at the top of README.md. For the condensed per-version history, see `docs/VERSION_HISTORY.md`.

## v0.23.20-dev

*Source: README.md:118 (the "Segment B" paragraph below it is README.md:120).*

v0.23.20-dev closes the **blind spot that let the previous round's `u8`-parameter defect survive five releases**. The v0.23.19-dev repair was correct, but round 4's diagnosis (82 probes) showed *why* the defect had gone unnoticed: **no example in the tree ever passed a `u8`/`u16`/`i64` argument**, so the 261-line A/B byte baseline (`tests/baseline/v0.23.5-dev/example-hashes.txt`, consumed by `tests/struct-checks.sh` [4/8]) was blind to that path — it could not have caught the regression even had it wanted to. This release wakes the baseline up and turns the diagnosis into a permanent asset. (1) Four new examples — `examples/narrow_args.ast` (narrow arguments in registers), `examples/narrow_return.ast` (narrow returns), `examples/narrow_stack_arg.ast` (narrow arguments on the 9th/10th stack slots, past the eight AAPCS64 register arguments), and `examples/narrow_so.ast` (a shared object exporting narrow-parameter functions for cross-language calls) — now carry narrow values, so the baseline records their three-mode output byte for byte: **261 → 273 lines, the other 261 unchanged**. (2) A new resident suite `tests/narrow-value-coverage.sh` [4/4] freezes the round-4 probes with the discipline the diagnosis itself demanded: **expected values are generated by `aarch64-linux-gnu-gcc` at run time, never hand-computed**. Each of its 16 cases has an Aster source and an equivalent C source; the suite compiles and runs both under qemu and asserts their two 8-bit exit codes are equal, so a disagreement is a real defect and not a miscalculation (three of the round-4 "failures" were the author's own arithmetic). Its [4/4] cross-language `.so` test — Aster's `.so` loaded from a C host through `dlopen`/`dlsym` — is the only witness that Aster's narrow-argument *stack layout* matches the platform's (gcc's); an Aster-calls-Aster test would pass on a layout nothing else uses. (3) The round-4 probe of the *other* faces — `bool` storage/passing, string/rodata boundaries, run-time global-init order, struct-array fields, multi-file link signature consistency — found **zero real defects**, and those faces remain covered by their dedicated suites (`bool-checks.sh`, `c-string-literals-*`, `e2e-global-deep.sh`, `struct-checks.sh`, `linker-checks.sh`/`symtab-checks.sh`); the gap was narrow *values* and only narrow values. Full CI: **all suites green, 0 failed**.

**Segment B (same release, no compiler delta):** the "other faces" claim is now backed by a resident check rather than an assertion. `tests/compiler-other-faces-audit.sh` [4/4] probes the three residual edges those dedicated suites had *not* exercised — byte-indexing a string pointer passed to an Aster-defined function (`load_u8(s+i)`), two distinct rodata literals addressed independently by offset, and a narrow `u8` argument carried across a **pure-Aster `link-obj`** (segment A had proven the narrow-argument ABI only against gcc via a `.so`) — every case gcc-differential (no hand-computed expectation), plus a [4/4] coverage-map assertion that the seven dedicated suites and the two failure-mode-mirroring edges (`u8_struct_field`, cross-file `runtime_init_order_*`) still exist. It passes; full `tests/ci.sh` is **77 passed / 0 skipped / 0 failed (of 77 checks)**, up from 76, the one new check being the audit suite. The five other faces are closed by evidence, not by claim.

## v0.23.19-dev

*Source: README.md:122.*

v0.23.19-dev fixes the defect that made **a `u8` argument never arrive**: `fn g(a: u8) : u8 { return a; }` called as `g(200)` returned **0**, and had never returned anything else — a `u8` parameter has not worked since `u8` was introduced in v0.23.2-dev. It never looked like an ABI problem, because `u8` locals, globals, array elements and struct fields were all correct, and that is what made it take a round to find: the cause is one line of encoding arithmetic. AArch64's unsigned immediate offset is **width-scaled**, so its *range* differs for every width — `LDRB`/`STRB` carry the byte offset **unscaled** in 12 bits (0..4095), `LDRH`/`STRH` scale by 2, `LDR`/`STR W` by 4 and `LDR`/`STR X` by 8. `loadStackT`/`storeStackT` shifted the byte offset left by 10 for *every* width, so for `u8` an offset past 4095 was neither rejected nor wrapped onto a neighbouring byte: bit 12 of the offset landed on **bit 22**, the one bit that separates `STRB` (`0x39000000`) from `LDRB` (`0x39400000`). Every call argument is staged in the scratch area at `4160 + callDepth*256`, which is past 4095 for *every* call, so the caller **stored** the argument by loading it and handed the callee whatever the uninitialized stack held. `u16` survived on arithmetic alone (`4160/2 == 2080` fits, and even the deepest scratch — `4160 + 14*256 + 31*8 == 7992` — is 3996 after the shift); struct fields cannot reach it (a struct is capped at 1024 bytes); locals and globals sit at small offsets. The repair is `stackOffFits()`, which decides **per width** whether an offset is expressible, and `loadStackOff`/`storeStackOff`, which stage the address through `x16` (or `x17`, when `x16` is itself the operand) when it is not. A fitting offset keeps the encoding it always had, so **no pre-existing output changes by a byte: 261/261 identical** across three modes. Covered by `tests/narrow-int-abi-checks.sh` [7/7]: a strict `-Werror` build, **15 source guards**, 2 rejections (`i64` into a `u8`/`u16` parameter), **24 qemu cases in five groups (three of them through a real cross-language link)**, 8 differential comparisons against cross-compiled C, and a **real cross-language link** — Aster's object linked against an `aarch64-linux-gnu-gcc` object — which is the only witness that the *stack layout* of a narrow argument (how far the 9th sits from the 10th) agrees with what the platform actually uses. Six compiler mutations, each a different way to lose a narrow argument, all have to be caught.

## v0.23.18-dev

*Source: README.md:124.*

v0.23.18-dev fixes the wide-integer correctness holes behind the new operators, and the headline is one line: **`let x: i64 = 4294967297; return x % 7;` used to return 1 — the correct answer is 5.** Three defects stacked. (a) `exprType` reported every numeric literal as `i32`, so although a literal reaching an `i64` slot was materialized at full width (`MOVZ`+`MOVK`), the five arithmetic sites then sign-extended it *from i32* and chopped the high bits back off: `return 4294967296 / 1000;` gave 0. (b) The width of an operation was decided by its **consumer** (`tyIs64(want)`) and never by its operands, so an `i64` value met by an `i32` context was computed in 32 bits. (c) `slotElemTypes` was declared and read but never written, so `elementTypeOf` fell back to `i32` for *every* local array: a local `i64[2]` addressed its elements at 4-byte stride while storing them 8 bytes wide, reading back neighbours' bytes. The repair is three rules, each pinned by the suite: **a constant operand whose value exceeds i32 makes the operation 64-bit** (`constExceedsI32`, magnitude tested after peeling `Neg`, thresholds `0x7fffffff`/`0x80000000`); **widening is the operand's own job, not the consumer's** — every post-hoc `SXTW` is deleted and the eight leaf forms (literal, `Neg`, local/global variable, field, three index forms, deref, call, conditional arm) widen themselves from their own type; and **an operation is 64-bit if either operand is i64 or over-wide, whatever the consumer wants**. `Cond` now takes its arm type from the expression when the consumer is `i32`, so `c ? big : small` keeps both arms wide. The dead `extendTo64` helper is deleted (zero references, and the suite guards that it stays gone). Covered by `tests/wide-int-literal-checks.sh` [7/7]: a strict `-Werror` build, **22 source guards** (each rule's helper and threshold, each of the eight widening sites, the dead helper's absence), 2 rejections (`i64` into an `i32` parameter; a literal that overflows i64), **54 qemu-run cases in eight groups** (wide literals consumed as i32, i64 locals across all operators, i64 operands with i32 consumers, `INT64_MIN`, leaf widening, conditional arms, local array element types, and six cases that must *stay* 32-bit), **14 differential comparisons against cross-compiled C**, and a **16-mutation layer** that rebuilds the compiler with each rule broken in turn and demands a named case go red. Three blind spots are documented rather than papered over: a consistently-truncated expectation (`8589934593 == 8589934593` passes when both sides lose their high bits, so every expectation is a large *positive* constant or compares against a small one), `&` cannot see a sign extension (`x & 7` discards the high half either way), and a `u32` return must not be widened. Byte-level: **259/261** outputs byte-identical to v0.23.17-dev across three modes; the two that differ are both `c_struct_abi` (`build-so`, `build-obj --pic`), the array-layout fix reaching a struct's `i64` field array, and `tests/e2e-c-struct.sh` links that example against a C host with 15 assertions both ways to show the change is behaviour-preserving — the 261-line baseline's two affected rows were re-recorded, the other 259 reproduce exactly.

## v0.23.17-dev

*Source: README.md:126.*

v0.23.17-dev gives the language the operators it never had: **`%`, `<<`, `>>`, `&`, `|`, `^`, `~`, the compound assignments (`+=` … `^=`), `++` / `--`, and `?:`**. Until this release the arithmetic vocabulary was `+ - * /` and the comparisons, so a remainder had to be written `a - a / b * b`, a bit mask was unreachable, and `glyph_bit` in the icon demo was division-and-modulo. The grammar now has a full precedence chain (`* / %` → `+ -` → `<< >>` → relational → equality → `&` → `^` → `|` → `&& ||` → `?:`), and every encoding was **read off `aarch64-linux-gnu-gcc -O2` output** for the equivalent C, not derived by hand: `%` is `SDIV` followed by `MSUB`, `>>` is `ASR` for a signed left operand and `LSR` for an unsigned one, `~` is `ORN` against the zero register. Compound assignment is desugared in the parser (`x OP= e` becomes `x = x OP e`), so no codegen path changes — and because that desugaring would otherwise evaluate a target's address twice, `a[f()] += 1` is rejected rather than silently miscompiled. `++` / `--` are statements only, never expressions, which is what keeps an Aster expression free of side effects. Covered by `tests/operator-checks.sh` [8/8]: 14 rejections, 30 qemu-run semantic checks, **11 differential comparisons against cross-compiled C**, and a mutation layer that rebuilds the compiler with `MSUB`→`MADD`, `ASR`→`LSR` and `ORN`→`ORR` to prove the checks test the encodings and not merely the parser. Byte-level: **214/214** outputs byte-identical to v0.23.16-dev across three modes, and the 261-line baseline reproduces exactly.

## v0.23.16-dev

*Source: README.md:128.*

v0.23.16-dev hardens the test infrastructure: **the e2e suite now executes on every host instead of being skipped on x86**. Until this release `ci.sh` chose its C host compiler by "what can run here", so on a non-AArch64 machine 23 of 72 checks silently reported SKIP — the C-ABI interop suites, the suites that prove Aster's calling convention against a C compiler, are exactly the ones a codegen change can break, and they were the ones not running on the main development machine. `ci.sh` now always selects `aarch64-linux-gnu-gcc` when it exists: the hosts are compiled **for the target architecture** and executed through the existing `tests/run-aarch64.sh` router (native on AArch64, `qemu-aarch64 -L /usr/aarch64-linux-gnu` elsewhere), so "must run on this machine" is replaced by "must run on the target". Result: **71 passed, 0 skipped, 1 failed on the first run** (the failure is `version-checks.sh` demanding this documentation), and **72/72** after it — where v0.23.15-dev reported 49/23/0 on the same machine. ## v0.23.15-dev

*Source: README.md:130.*

v0.23.15-dev is the hotfix that makes **`examples/native_touch.ast` actually answer a finger** — v0.23.14-dev shipped it with three stacked defects, and on a real device it drew the gradient and ignored every touch. The callbacks were wired at the wrong offsets (`onInputQueueCreated` at 80, but 80 is `onNativeWindowDestroyed`; the input queue is 88/96), the event drain tested `got == 1` (`AInputQueue_getEvent` signals success with **0** and a dry queue with a negative value), and the coordinates were read as `i32` from `w0` — while a C `float` return actually sits in **s0**, a different register file. The fix for the third one is a bridge rather than a compiler feature: Aster emits no SIMD instruction and the PLT is eagerly bound, so the `s0` a float-returning call leaves behind survives to the next call — and a zero-argument **`lrintf()`** (argument in s0, `long` result in x0) issued immediately after `getX`/`getY` hands Aster the exact integer. That is the one real compiler edit: `ndkLibraryFor` now maps `lrintf` → **libm.so**, without which the on-device loader would abort `dlopen`. The qemu test was testing the decoder while the capture was what was broken, so it now exercises the capture itself: `strtof` — also a C float-returning function — stands in for `getX`, the `.so` is dlopened by `tests/touch-coord-host.c`, and the mutation layer breaks the bridge (`return lrintf();` → `return junk;`, literally the v0.23.14-dev bug) and requires the test to go red. The example also logs its pipeline to logcat on fixed strings, so the next "it does nothing" comes back with evidence. Code generation for pre-existing code is untouched: **212/212** outputs byte-identical to v0.23.14-dev; the only current-source delta is `native_touch.build-so`, which differs by exactly the `lrintf` → `libm.so` `DT_NEEDED` remap.

## v0.23.13-dev

*Source: README.md:131.*

v0.23.13-dev answers the question **"who checks that my `extern` matches the function I actually wrote?"** — nobody, until now. A two-file program shared a signature by *retyping* it, and because the linker matches by name, a retyped arity or return type linked, ran, and returned garbage without a word. **`include "PATH";`** now brings another file's declarations into this one, and what crosses is **the signature read out of the file that holds the body** — so it cannot drift, because it is not a second copy. Declarations only: a body and an initializer stay in the file that owns them, the two files still compile to two objects, and nothing about the object format or the ABI changes. PATH resolves against the **file that wrote it** (C's `#include` rule) with `--include-dir DIR` overriding; including the same file twice is a no-op, a cycle is an error that names the chain, and a definition in this file **supersedes** the included declaration, so "include the header, then define the functions" is legal. The proof is byte-identity rather than "it built": an object built with `include` is **`cmp`-identical** to one built from a file that hand-writes the same `extern` lines — and `add2`/`total` must be `UND` in it, which is what "the body stayed in the other file" looks like. Covered by `tests/include-checks.sh` [12/12], including four compiler mutations that each have to be caught. Code generation for pre-existing code is untouched: **210/210** outputs are byte-identical to v0.23.12-dev.

## v0.23.12-dev

*Source: README.md:132.*

v0.23.12-dev answers the question "which `.ast` line produced this instruction?" — until now the answer was "count backwards by hand", because nothing Aster emitted named a source line at all. **`-g` / `--debug-line` now emits a real DWARF v4 `.debug_line` table**: one row per statement, at the instruction the statement begins at, naming the source file — so a debugger can answer "where does a breakpoint for line 12 go?" and a crash address can be turned back into a line. The rows come from the source positions v0.23.10-dev threaded through the AST, recorded at every statement boundary in `Codegen` (a nested body goes through the same path, so every depth is covered) plus one row per function **prologue**, attributed to the line that *declares* the function rather than to its first statement. The one genuinely new problem is that a relocatable object does not know its own address: each address is therefore written as 0 and carried by `.rela.debug_line` as `R_AARCH64_ABS64` (257 — a relocation type Aster had never emitted) against a local `.text` section symbol, and both linkers raise it to that object's final text address — which is also how linking two `-g` objects yields **one unit per object**, each covering its own range. The output is **strictly additive**: new sections are laid out after everything that already existed, so `-g` cannot move a single byte of `.text` (asserted by `cmp` on `readelf -x .text`), and without the flag the compiler takes none of these paths. Proven by two independent readers — a decoder written for this suite (`tests/debugline-decode.py`) and `llvm-dwarfdump` — which must agree **row for row**; the assertion that matters is the *line set*, which must equal exactly the statement lines of a known source, no more and no fewer. Covered by `tests/debugline-checks.sh` [9/9], whose last check injects an off-by-one into a copy of the source and requires the suite to notice. Code generation for pre-existing code is untouched: **40/40** executables, **84/84** objects and **84/84** shared objects are byte-identical to v0.23.11-dev.

## v0.23.7-dev

*Source: README.md:133.*

v0.23.7-dev answers the question "can we skip `resources.arsc` and put everything in one `.so`?" — **no for resources the Android framework reads, and the way out is to make the table real rather than to delete it.** `android:icon` and `android:label` are *resource ids* (`0xpptteeee`), not paths and not strings; the id → value mapping exists only in `resources.arsc`, and a resource the table does not hold resolves to 0 — the app installs, nothing is logged, and the launcher shows the generic icon with a blank name. So this release does two things. **The table becomes a table**: any number of types, any number of entries, ids derived from the table itself (`0x7f010000` `drawable/ic_launcher`, `0x7f020000` `string/app_name`, …), `--string NAME=VALUE` adding inline strings, and `android:label` naming `string/app_name` — spelled out in the manifest by default, or as a `TYPE_REFERENCE` with `--label-as-reference`, because a reference is only a promise to open the table and not every APK viewer keeps it. **And Aster's own resources get a syntax**: `@embed("path")` reads a file at compile time and yields the address of its bytes in `.rodata`; `@embed_len("path")` folds to the byte count as a compile-time constant, so it works as an array bound or a global initializer. Paths resolve against the source file's own directory (C `#include` rules) with `--embed-dir` overriding, and the same file embedded twice is embedded once. Covered by `tests/resource-table-checks.sh` [6/6] and `tests/embed-checks.sh` [6/6]. Cross-checked by androguard's `ARSCParser`, which resolves all four resources of a test APK, and by `AXMLPrinter`, which renders `android:label="@7F020000"` for the `--label-as-reference` build and the bare name for the default one. Code generation for pre-existing code is untouched: **252/252** outputs are byte-identical to v0.23.5-dev.

## v0.23.6-dev

*Source: README.md:134.*

v0.23.6-dev gives Aster-built APKs a **launcher icon** (P2.2). `android:icon` is a *resource id*, not a path, and the mapping from that id to a file exists only inside `resources.arsc` — ship the PNG without the table and the id resolves to 0, so the app installs, nothing is logged, and the launcher shows the generic Android icon. ## v0.23.5-dev

*Source: README.md:135.*

v0.23.5-dev adds **structs** (P3.3): a nominal composite type that travels by value under the **full AAPCS64** rules. `struct Point { x: i32, y: i32 }` declares one, `Point { 3, 4 }` builds one, `p.x` reads a field and `p.x = 5` writes one, `let q: Point = p` copies the whole value, a field may be another struct, and `ptr<Point>` reached with `&p` is a distinct type. Types are **nominal** — two structs with identical layouts are still different types — and a struct is a value but not an integer: `p + 1`, `p == q` and `if (p)` are all rejected. Crossing a call, a composite of ≤8 bytes goes in one register, 9..16 bytes in a consecutive pair, and anything larger is copied by the caller with its **address** passed instead (8-byte slot, even on the stack); a >16-byte result comes back through the buffer whose address the caller puts in **X8**. Both call sides call one shared `layoutArgs()`, so they cannot disagree, and the layout is checked **byte for byte against a C compiler**. Globals, nesting and aggregate literals in constant initializers are supported. Covered by `tests/struct-checks.sh` [8/8] and `tests/e2e-c-struct.sh` (which links Aster's half against a C host and checks all three classes in both directions). Code generation for pre-existing code is untouched: the **246** recorded outputs of the 82 pre-existing examples are byte-identical.

## v0.23.4-dev

*Source: README.md:136.*

v0.23.4-dev makes the **signing key an input instead of a constant** (P2.5). Until now every APK was signed with one RSA key compiled into the binary, so two developers' APKs carried the same identity and nobody could ship under their own; Aster also had no way to check a signature it had just made. Signing now takes a `SigningKey` chosen at build time: **`--sign-mode debug`** (the default) uses a per-project key Aster generates on first use with `aster keygen` and stores in `<project>/.aster/`, while **`--sign-mode release --keystore <key.pem> --cert <cert.pem>`** uses yours — and release **fails closed**: without both options the build stops rather than quietly signing with a debug key. Key material is read as PEM or DER (PKCS#8 or PKCS#1 private keys, X.509 certificates), so anything `openssl` or `keytool` wrote loads directly, and a key whose certificate does not carry its own public half is rejected before any work is done. The new `aster verify-apk <app.apk>` re-derives the whole v1 + v2 chain — ZIP CRCs, JAR digests, the PKCS#7 signature, the APK Signing Block structure, the chunked content digest and the RSA signature over signed-data — and `build-apk` now runs that very verifier **on the in-memory APK before writing it**, so a bad signature cannot reach the disk (`--no-verify` bypasses only the check, never the signing). `src/aster_apk_key.h` is gone: Aster ships with no key of its own. Covered by `tests/signing-checks.sh` [10/10], which uses `openssl` as an independent oracle on the generated key material. Code generation is untouched: **204/204** outputs are byte-identical to v0.23.3-dev.

## v0.23.11-dev

*Source: README.md:137.*

v0.23.11-dev adds a **syntax fuzzer** (P4.4). The parser is the one component every input reaches, and it is the one that has actually taken the compiler down — v0.23.10-dev shipped with six `z->a = std::move(x); z->line = x->line;` sites that read a moved-from `unique_ptr` and crashed on legal programs (a negative literal, a `!`, a `*p = v`), caught only by the full CI. `tests/fuzz-checks.sh` now throws **2,000 seeded inputs** at the compiler — fixed seeds for the paths that have crashed, single-edit "light" mutations of real examples (nearly valid, so they get deep), token soup for the lexer, and valid frames filled with random statements — and asserts one property: **every input either compiles or is rejected cleanly, never crashes**. A subset also takes the `build-obj --pic` and `build-so` paths, which carry different codegen (PLT/GOT, relocations). Two guards keep the suite honest: it asserts a nonzero share of the corpus actually compiles (so the corpus cannot degrade into "everything is rejected at the first token"), and it **re-injects the v0.23.10-dev bug into a copy of the source and requires the fuzzer to crash it** — a fuzzer that cannot fail is not evidence. Current run: 2,000 inputs, **0 crashes**, 76 compiled, 301 more through the `.o`/`.so` paths, 34 s.

## v0.23.3-dev

v0.23.3-dev gives `build-apk` an **APK v2 signature** (P2.1) alongside the existing v1 (JAR) signature, so the APKs Aster produces are now **dual-signed**. `build-apk` inserts an `APK Sig Block 42` between the last ZIP entry and the Central Directory, carrying one v2 signer under algorithm `0x0103` (RSASSA-PKCS1-v1_5 + SHA2-256 — chosen over the PSS variants because it is deterministic, so Aster builds stay byte-reproducible). The CHUNKED_SHA256 content digest covers the ZIP entry region, the Central Directory and the EOCD in 1 MiB chunks; the one subtle rule is that the EOCD is *digested* with its "offset of start of central directory" rewritten to the Signing Block start, while the record actually *written* keeps the real Central Directory offset, so both ZIP tools and the verifier agree. `CERT.SF` gains `X-Android-APK-Signed: 2`, which is what makes stripping the v2 block and downgrading the APK to v1 detectable. **v3 is deliberately not implemented**: its only incremental value is key rotation, which a fixed embedded dev key has no use for, and its `minSdk`/`maxSdk` attributes add failure modes for no benefit — v1 + v2 is the actual compliance gate. The v2 public key is lifted out of the embedded certificate rather than duplicated, so the two can never drift. Cross-checked against Google's own `apksig` 8.7.3 `ApkVerifier` (v1 and v2 both verify, zero errors and zero warnings) and re-derived from scratch by `tests/validate_apk.py` [6]. Code generation is untouched: **204/204** outputs are byte-identical to v0.23.2-dev.

v0.23.2-dev adds the **wider integer types `i64` / `u8` / `u16` / `u32`** (P3.2). The old scattered `isPtr`/`isBool` booleans are replaced by a single unified `Ty` lattice (`i32`, `u32`, `u8`, `u16`, `i64`, `ptr`, `bool`) that drives every load/store/arithmetic/compare choice; a latent wide-literal bug is fixed (the `MOVK` base no longer over-shifts, so i64 constants larger than 32 bits materialize correctly); narrow types use zero-extending `LDRB`/`LDRH`/`STRB`/`STRH`; unsigned types take `LO`/`LS`/`HI`/`HS` condition codes and `UDIV`; and i64 travels the 8-byte AAPCS64 ABI (`x0`–`x7`, stack slots for args 9+). Wide and narrow globals and array elements are supported. Every pre-existing `i32` example still compiles **byte-identically** — the new width logic defaults to the i32 path. Covered by `tests/wide-int-checks.sh` [8/8]: source guards, a rejection matrix (narrowing, unsigned-range and literal-range misuse), qemu self-checks for i64 arithmetic/comparison/ABI, narrow unsigned wrap/UDIV/cmp, wide/narrow globals and array elements, and a regression step for the two latent bugs below. The same release fixes two latent encoding bugs found by comparing all 82 examples against the previous release: the `LDRH`/`STRH` immediate is scaled by the 2-byte access size and was being handed a raw byte offset (a `u16` local landed in its neighbour's slot), and the rewritten function prologue loaded every incoming stack argument with a hardcoded 64-bit `LDR X16` instead of the width of its declared type (4 examples changed bytes). Both are fixed and guarded; the A/B comparison is now **82/82 byte-identical**. v0.23.1-dev closes the other half of array safety with **`--bounds-check`** (P1.5). Constant out-of-bounds indexes have long been a compile-time error; an index whose value is only known at run time still read or wrote neighbouring memory in silence. The new opt-in flag lowers every dynamic index into a fixed-size array — global or local, read or write — into `CMP widx, #len` + `B.LO` over a `BRK #1`, so an out-of-range access raises **SIGTRAP** instead of corrupting memory. One unsigned comparison covers both halves of the range, because a negative index is a huge unsigned value. The flag is **off by default**: an ordinary build emits the bytes it always did (all 82 examples are byte-identical), and a program that only indexes with constants is unchanged even with the flag on. Compile-time rejection still wins — a constant index is proved in range by the existing fold and gets no run-time test. The same release fixes a latent encoding bug found on the way: `CMP Wn, #0` was emitted as `SUBS` with `Rd = w0` instead of `Rd = WZR`, silently overwriting a live expression temporary (`0x71000000 | reg << 5 | 31` now, verified by disassembly and guarded by a source check). Covered by `tests/runtime-bounds-checks.sh` [8/8]: source guards, flag routing (the link commands must reject it), the constant-index proof, structural trap counts, qemu runs of the in-range and out-of-range paths, and a bit-level check of the `BRK #1` encoding. v0.23.0-dev moves **type checking into a standalone semantic pass** (P3.1). Every emitted function is now walked and type-checked — declarations, assignments, indexing and its constant-folded bounds check, dereference, call arity and argument types, return types, and the `if`/`while`/`for` condition rule — **before** code generation starts, with its own scope stack and a three-type lattice (`i32`, `ptr`, `bool`), instead of being checked as a side effect of emitting instructions. Constant folding and comparison classification were hoisted to file scope so the semantic pass and codegen share one definition and cannot drift apart. Codegen keeps its checks as a defensive backstop, so a rule can be duplicated but never silently dropped: all 82 examples still compile **byte-identically** and every pre-existing rejection still reports the same message.
