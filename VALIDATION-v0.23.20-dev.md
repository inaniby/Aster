# Validation — v0.23.20-dev

> Round 4. The previous round (v0.23.19-dev) fixed the `u8`-parameter defect.
> This round answers the harder question *why that defect survived five
> releases* and closes the gap for good: the A/B byte baseline could not see
> the narrow-argument path, and the round-4 probes are frozen into a resident
> suite whose expectations are generated by the compiler, not by hand.

## 1. Why round 4 exists: the baseline was blind by construction

Round 3 proved the `u8`-parameter fix correct (`stackOffFits` + `loadStackOff`/
`storeStackOff`, `tests/narrow-int-abi-checks.sh` [7/7]). Round 4 then asked:
*why did this defect live from v0.23.2-dev through v0.23.18-dev?* The 82-probe
diagnosis answered it, and the answer was not another bug. **No example in the
tree ever passed a `u8`/`u16`/`i64` argument.** All 87 `examples/*.ast` pass
`i32`/`ptr` arguments; the narrow types appear only as locals, globals, array
elements and struct fields. So `tests/baseline/v0.23.5-dev/example-hashes.txt`
— the 261-line A/B byte baseline asserted by `tests/struct-checks.sh` [4/8] —
enumerates `examples/*.ast` and records every example's output in three modes.
If no example passes a narrow argument, **nothing in the baseline exercises
that path**, and a regression there is invisible by construction. The defect was
not overlooked; it was unobservable to the one check that should have caught it.

## 2. The two-part repair: make the blind spot visible and permanent

1. **Wake the baseline up.** Four new examples carry narrow values through the
   exact path the baseline could not see:
   - `examples/narrow_args.ast` — `u8`/`u16`/`i64` arguments delivered in the
     eight AAPCS64 registers;
   - `examples/narrow_return.ast` — functions returning `u8`/`u16`/`i64`,
     consumed by `main`;
   - `examples/narrow_stack_arg.ast` — narrow arguments on the **9th and 10th**
     stack slots (the `4160 + callDepth*256` scratch area, past the 4095
     unscaled-byte limit, which is exactly where the v0.23.19-dev defect lived);
   - `examples/narrow_so.ast` — a shared object exporting `u8`/`u16`/`i64`
     parameter and return functions, for cross-language calls.
   Re-running the baseline generator over all examples records **273 lines
   (was 261); the other 261 are byte-identical**.
2. **Freeze the diagnosis as a resident suite.** `tests/narrow-value-coverage.sh`
   [4/4] turns the round-4 probes into a permanent check (registered in
   `ci.sh` after `narrow-int-abi-checks.sh`). Its defining property is in §5.

## 3. The four new examples, byte for byte

Each new example compiles in `build-so`, `build-elf` and `build-obj --pic`
(`narrow_so.ast`, having no `main`, records `build-elf FAILED` like the other
`.so` examples). Their three-mode output is added to the baseline, so any
future regression in narrow-argument *emission* is caught byte for byte — which
is precisely what the pre-v0.23.20-dev baseline could not do. The baseline now
reproduces **273/273**: the 261 pre-existing rows are unchanged (the version
constant is not embedded in generated objects, so bumping it moves no byte), and
12 new rows cover the four examples.

## 4. `tests/narrow-value-coverage.sh` — four layers, all run

- **[1/4] Strict rebuild** (`-Werror`): clean.
- **[2/4] Locate an AArch64 C compiler** (the independent oracle). If
  `aarch64-linux-gnu-gcc` is absent, the suite SKIPs cleanly (exit 0 with a
  SKIP line) — it never fails for a missing toolchain. With the toolchain
  present (this tree), it confirms the compiler emits AArch64 ELF.
- **[3/4] Differential battery**: 16 cases. Each has an Aster source and an
  equivalent C source covering narrow arguments in registers, a second narrow
  argument, `u16`/`i64` passthrough, mixed narrow arguments returning `i64`, a
  narrow argument through a nested call, an `i64`+`u8` combination, the 9th/10th
  stack-slot narrow arguments, a narrow return consumed in `i32`, a `u8` struct
  field, a `u8` `while` loop, `u8` recursion, and `u8`/`u16` global arrays. The
  C source is compiled by `aarch64-linux-gnu-gcc -O2 -fwrapv` and run; its
  8-bit exit code is the expected value, asserted equal to Aster's.
- **[4/4] Cross-language `.so`**: Aster's `narrow_so.ast` is built into a shared
  object and loaded from a C host through `dlopen`/`dlsym`, which calls
  `add_u8(100,50)`, `add_u16(40000,25535)`, `scale_i64(1000000,7)`,
  `ninth_u8(0,0,0,0,0,0,0,0,200)`, `ret_u8()`, `ret_u16()` and asserts all six.

## 5. The discipline that matters: expectations are generated, not written

Round 4's own 82-probe sweep produced five "failures"; three of them were the
*author's* mistakes — `4000000000 % 7` taken as 6 (it is 3), `load_u8(p)` read
as `a[0]`, and a couple of syntax slips (`if` needing `else`, no `true` literal,
an `include` whose definition object was not linked). The suite would have
reported a defect that did not exist. `narrow-value-coverage.sh` removes that
failure mode by construction: **it holds no expected number.** For every case
it compiles the C oracle, runs it, and compares Aster's exit code to gcc's. If
they agree, the case passes; if they disagree, the case is a real defect. There
is no expectation for the author to miscalculate. This is the discipline the
round-4 verdict demanded ("期望值全部由 aarch64 gcc 差分生成，不再手算").

## 6. Why the cross-language `.so` is the only true layout witness

An Aster-calls-Aster link would pass even on a narrow-argument *stack layout*
that no other toolchain uses, because both sides share Aster's own (possibly
wrong) convention. Only a C host — compiled by `aarch64-linux-gnu-gcc`, the
platform's own compiler — calling Aster's `.so` through `dlopen`/`dlsym`
proves the layout agrees with the platform: how far the 9th argument sits from
the 10th, the register-to-stack split, and the high bits of a returned `u8`
(which AAPCS64 leaves unspecified, so a C callee that reads them would read
something Aster never promised — the C side only ever compares values it
normalizes itself). [4/4] is that witness, and it returned 0 (all six signatures
correct).

## 7. The other faces round 4 probed are clean

The 82-probe sweep also exercised `bool` storage/passing, string/rodata
boundaries, run-time global-initializer order, struct-array fields and
multi-file link signature consistency. It found **zero real defects**. Those
faces remain owned by their dedicated suites — `bool-checks.sh`,
`c-string-literals-*` + `e2e-c-string-literals.sh`, `e2e-global-deep.sh`,
`struct-checks.sh`, and `linker-checks.sh`/`symtab-checks.sh` respectively. The
gap was narrow *values* and only narrow values; this release closes exactly
that and leaves the rest alone. No compiler codegen change was needed this
round — round 3 already produced correct narrow-argument output, and this round
makes that correctness *observable*.

## 8. Byte identity: 273 of 273

The A/B byte baseline reproduces exactly: 261 pre-existing rows byte-identical
to v0.23.19-dev, plus 12 new rows for the four examples across `build-so` /
`build-elf` / `build-obj --pic`. `struct-checks.sh` [4/8] asserts the baseline
and passed. Direct A/B over every example in three modes shows no pre-existing
row changed.

## 11. What this unblocks

The narrow-value path is now observed by *two* independent mechanisms: the A/B
byte baseline (catches emission regressions) and a gcc-differential resident
suite (catches behaviour regressions, with expectations no human can get wrong).
A defect like the v0.23.19-dev one — a narrow argument that silently fails to
arrive — would now be caught on the first CI run, by the baseline if it moves a
byte and by `narrow-value-coverage.sh` [3/4] if it merely misbehaves. The
type-width × storage/parameter-location matrix that round 4 confirmed closed is
now permanently guarded, and the round-4 diagnosis is no longer throwaway: it is
a checked-in asset.

## 12. Segment B — the "other faces" deep-dig (closure audit)

Round 4's headline fix closed the narrow-value path. The user's second
instruction was to *keep digging into the compiler's other faces*. The round-4
diagnosis had claimed those faces were clean, but a claim is not a check. This
segment turns the claim into a resident asset.

### 12.2 The new resident asset: `tests/compiler-other-faces-audit.sh`

Four layers, same discipline as `narrow-value-coverage.sh` — every case has an
Aster source **and** a C twin, the C twin is the oracle, both build and run under
qemu, and the two 8-bit exit codes must match; no expected number is hand-written.

* `[1/4]` strict compiler build (`-Werror`)
* `[2/4]` locate `aarch64-linux-gnu-gcc` (the oracle); SKIP cleanly without one
* `[3/4]` differential battery — 2 rodata/string edges:
  * `string_byte_index_across_call`: `fn at(s: ptr, i: i32) -> i32 { return load_u8(s + i); }` called with `"ABC"` at index 1 → 66 (`'B'`), gcc-differential
  * `two_string_literals_offset`: two literals `"XY"`/`"ZW"` read by offset → `88 + 87 = 175`, gcc-differential
  * `[3b]` narrow `u8` argument across an Aster<->Aster `link-obj` (define in TU-A, `extern` + call in TU-B), cross-asserted against a gcc<->gcc link → `200 + 1 == 201`
* `[4/4]` coverage-map assertion: the 7 dedicated suites for the other faces still
  exist, and the two edges that mirror the narrow-argument failure mode
  (`u8_struct_field`, cross-file `runtime_init_order_*`) are still present — so the
  coverage map cannot silently rot

### 12.3 Result

The audit passes. Every residual edge the existing suites had missed now agrees
with gcc exactly, and the multi-file narrow-argument ABI that segment A had only
proven against C is confirmed on the pure-Aster link path. The five "other faces"
are therefore **closed by evidence, not by assertion**: each is either guarded by
a dedicated resident suite or proven clean by a gcc-differential probe in this
audit. Full `tests/ci.sh` after this segment: **77 passed / 0 skipped / 0 failed
(of 77 checks)** — up from 76, the one new check being `compiler-other-faces-audit.sh`.
