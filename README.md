> v0.23.41-dev adds **raw memory** — `mmap` and `brk`, the second hard blocker on the self-hosting route (`SELFHOSTING-PLAN.md` M1). M0's round ended *"No heap, no `argc`/`argv`"*, and the bootstrap's next need is bytes it can hand back: a compiler that reads a source file in has to put an AST somewhere. The design is deliberately allocator-free — two system calls, `mmap` (x8=222) and `brk` (x8=214), emitted as `SVC #0` exactly like the M0 four through the same factored `syscallInsn`, so Aster still owns **no allocator**; `examples/arena.ast` is the whole shape on top, a 25-line bump allocator over one 64 KiB mapping. `mmap(addr: ptr, length: i64, prot: i32, flags: i32, fd: i32, offset: i64) -> ptr` is the **widest intrinsic the language has** (six arguments, two of them `i64`) and `brk(addr: ptr) -> ptr` both *queries* (`brk(z)` answers the current break) and *grows* (a nonzero, page-aligned `addr` moves it). Two generalizations of `syscallInsn` carry the round, both forced by measurement: **a 64-bit result is read at full width** (`MOV Xd, X0` when the result type is `Ty::Ptr`/`Ty::I64`, the W half otherwise) — qemu hands out mappings near `0x4000_0081_2000` (~70 TB, high word nonzero), and a truncated read would collapse to `0x0081_2000` and fault on first access; and **an `i64` argument rides at full width** (the staging loop keys on `tyIs64`, not `== Ty::Ptr`) — a 4 GiB `length` staged through W becomes 0, and the kernel answers EINVAL. Codegen's `callType` learns the pair (`mmap`/`brk` answer `Ty::Ptr`), the first intrinsics besides `load_ptr` that do. The kernel's own rules *are* the contract: a failing call answers `-errno` in pointer form (an unaligned `offset` → `-22`, which is how the suite pinned that `mmap`'s offset must be page-aligned), and the null check is the program's job. Resident suite `tests/heap-checks.sh` [6/6]: 5 differential cases (a page poke at five offsets, a real 4 GiB mapping, openat→fstat→mmap-at-4096 of a real file, a `brk` query/grow/poke cycle, and `examples/arena.ast` against its C twin `tests/arena-twin.c`), 10 rejections, 2 shadow cases, and a 5-mutant layer. Baseline **324 → 327 lines**, the other 324 byte-identical.

> v0.23.36-dev makes **`--bounds-check` guard array *parameter* subscripts too**. The flag (since v0.23.1-dev) has trapped out-of-range local and global array accesses with a `BRK #1` (SIGTRAP, exit 133); a parameter was the one array shape it could not see, because the two length tables everything else reads from were never filled for a parameter. The round adds a third, narrow length table — `paramArrayLength[slot]`, filled from the parameter's dimensions and consulted *only* by the check sites — which is deliberately *not* `localArrayLength`, because `gen(Var)` keys off that map to decide whether a bare `a` resolves to the frame slot or to the decayed pointer (handing a parameter a `localArrayLength` entry would silently break every call that relies on the pointer). So `fn f(a: i32[4]) { a[i] }` and `a[i] = v` now emit the same `CMP widx, #len` + `B.LO` over `BRK #1` as a local/global array, a constant out-of-range subscript (`a[4]`) is still rejected at compile time flag or not, and a multi-dimensional parameter (`a[i][j]`) checks per dimension through the existing per-dimension path. A default build emits no test — `emitBoundsCheck` opens with `if(!boundsCheck) return;` — so **no pre-existing byte moves** (309 of 309 baseline rows, no new example) and the `--bounds-check` opt-in rule stands. New resident suite `tests/array-param-bounds-checks.sh` [8/9]: a strict rebuild, source guards, qemu acceptance (in-range read/write identical with/without the flag), trap acceptance (out-of-range read/write/negative → 133 under the flag, silent by default), multi-dimensional per-dimension checks, compile-time constant rejection, a gcc-differential twin (`tests/array-param-bounds-twin.c`, both exit 6), and a 2-mutant layer — closing the v0.23.34-dev/v0.23.35-dev *"parameter bounds check absent"* line.

> v0.23.35-dev lets a program **ask** the two numbers it used to have to hard-code: `sizeof` answers bytes — `sizeof(i32)` is 4, `sizeof(i32[4])` is 16, `sizeof(Row)` is the struct's laid-out size — and `len` answers the element count, the product of the dimensions, so `len(i64[2][3])` is 6 and not 2. Both accept a type and an expression (`sizeof(w)`, `len(row.cells)`, `sizeof(i32[4])`), both fold to an `i32` constant at compile time, and every downstream site sees an ordinary integer. The second half is what makes the first half answerable inside a function: since v0.23.34-dev an array may be a parameter, but the decay threw the length away, so `len(a)` had nothing to answer from — **`Function::paramDims` now carries the dimensions into the body** and `Sema::check` fills the binding with them, so `sizeof(a)` answers the array's 16 bytes and `len(a)` its 4 elements, while the parameter stays a pointer for every other purpose (`return a;` still refused, a subscript unchecked by default but now guarded under `--bounds-check` in v0.23.36-dev). One number is deliberately Aster's and not C's: `sizeof` on a decayed parameter in C is the pointer's 8; Aster answers the array the caller actually passed, and the C twin says so out loud by measuring a real array type. `len` refuses what has no element count — a scalar, a `ptr`, a scalar or struct *type* — each message naming the fix, and `sizeof` is total over the type grammar. **No program that compiled before changes by a byte**: 306 of 306 baseline rows reproduce, the 3 new ones belonging to `examples/sizeof_len.ast`; `tests/rebuild-baseline-v0.23.35.sh` asserts the pre-existing rows byte-identical before it writes anything. > v0.23.34-dev makes an array a **first-class thing a function can take and hand back**, and removes the last width limit on `&arr`. Until now `&buf` answered a plain `ptr` and `p[i]` on it always strode four bytes, so an `i64[4]` or `u8[4]` could not be reached by reference without mis-scaling or a rejection; and there was no way to pass a whole array to a function at all — every array a function touched was a global for exactly that reason. Three things move together. **An array parameter decays to a typed pointer** — `fn sum(a: i32[4]) -> i32` reads `a[i]` at the element's real width, and `fn sum64(a: i64[4])` does the same at eight — so a local `T[N]` crosses a call boundary as the address it already was, and a struct array parameter `fn get(v: V3[2]) -> i32` reaches `v[1].a`. **`&arr` is no longer width-gated**: `&buf` answers `ptr<i64>`, `ptr<u8>`, `ptr<V3>` … a `ptr<T>` carries its element's real byte width, and `p[i]` strides at that width in both Sema and Codegen (one `slotElemTypes` record, read by both passes, so they cannot disagree about the stride); `(&arr)[i]` indexes through the address directly. One honest guard comes with it: a strided pointer must not land in an **untyped** `ptr`, which would still index at four bytes and read the wrong element silently — `let p: ptr = &w;` on an `i64[2]` is refused and told to declare `ptr<i64>` or take the array as a parameter, and a `ptr<V3>` does not go into a `ptr<Q>`. **A function returns a typed pointer too** — `fn get(w: ptr<i64>) -> ptr<i64> { return w; }` round-trips a `ptr<i64>` through a call — and `return a;` from an array parameter is still refused as a dangling frame pointer. The round also closes the carry-forward **Lifecycle example**: `examples/lifecycle.ast` fills the seven `ANativeActivityCallbacks` lifecycle slots — `onStart`/`onResume`/`onPause`/`onStop`/`onDestroy`/`onConfigurationChanged`/`onLowMemory` at offsets 0..48 — which `native_render.ast` and `native_touch.ast` left empty, and `tests/lifecycle-callbacks.sh` drives all seven under `qemu-aarch64` by loading the example as a shared object, calling `ANativeActivity_onCreate`, invoking each installed entry and reading the counters back. **No program that compiled before changes by a byte**: 306 of 306 baseline rows reproduce, the 3 new ones belonging to `examples/lifecycle.ast`; `tests/rebuild-baseline-v0.23.34.sh` asserts the 303 pre-existing rows byte-identical before it writes anything. Updated resident suite `tests/array-address-checks.sh` [9/9] (stride capability, rejection matrix, source guards, gcc differential, mutation layer) and new `tests/lifecycle-callbacks.sh` cover the round.
> v0.23.33-dev is the second half of the debug-information story: **`.eh_frame`** — so a debugger can *walk* a stack, not only print the frame it stopped in. `-g` now emits a DWARF v4 **`.eh_frame`** (and its `.eh_frame_hdr`) beside the `.debug_line` and `.debug_info` it already wrote. Aster's frames are uniform — every function's prologue is exactly `SUB SP, SP, #8192` and SP never moves again inside a body — so a whole function's unwind table is **six bytes of CFI**: the CFA is `r31 (sp) + 8192` one instruction past the prologue, and the return address is stored at `CFA - 8` by every body that returns (the entry, which *exits*, does not save `x30`). The **CIE is byte-for-byte the one `aarch64-linux-gnu-gcc` writes** — augmentation `zR`, code alignment 4, data alignment −8, return-address column 30, `pcrel sdata4` — and the table is resolved by the same patch-site mechanism as `.debug_info`: every address field is carried by `.rela.eh_frame` as `R_AARCH64_PREL32` (261) in an object, and written directly by `build-elf`/`build-pie`/both `.so` paths and the linkers, so linking two `-g` objects yields one raised table and a shared object keeps every function's. Both sections ride in their own `PT_LOAD` under a `PT_GNU_EH_FRAME`, the header sorted and reachable, because an unwinder reads them out of the running image. **The output is strictly additive**: 303 of 303 pre-existing baseline rows reproduce byte for byte, and `-g` cannot move a byte of `.text`. New resident suite `tests/eh-frame-checks.sh` [9/9] — with `tests/ehframe-decode.py`, a decoder that reads the CIE/FDE bytes straight out of the ELF and runs the CFI program — proves the CIE equals gcc's, one FDE per function agrees with the symbol table, the CFA and return-address rules land where `objdump` says the prologue ends, the `.eh_frame_hdr` is sorted and reachable under `PT_GNU_EH_FRAME` in its own `PT_LOAD`, two independent readers (`readelf` and `llvm-dwarfdump`) describe the same functions and rules, and the table survives `link-obj`/`link-so` and running under qemu unchanged.

> v0.23.31-dev gives an array **a second subscript**: `T[N][M]`, with `a[i]` a **row** — the address of `M` elements — and `a[i][j]` the element, exactly as in C. Until now a subscript was the last thing you could do to an array: `a[i]` *was* the element, and that was the end of the expression. **No new type carries it**: an array name already decays to a `ptr` (v0.23.30-dev made that address reachable by name), so a row address is the same decay one level in — `a` is a ptr, `a[i]` is a ptr, `a[i][j]` is `i32`. The whole round is therefore a question of **stride**: a subscript at dimension *k* strides by `dims[k+1] * … * dims[L-1] * sizeof(elem)`, which for the innermost subscript is the element size — the one stride a one-dimensional array has always had — and for an outer one is the product of the dimensions below it (12 for a row of a 2×3 `i32` grid, 24 for a row of a 2×3 `i64` one). Five places moved together. **`arrayDimList()` reads one `[N]` per dimension** at every declaration site — a local, a global in all three branches, a struct field — while `count` stays the *total* element count, so the frame reservation, the broadcast initializer, `.data`/`.bss` sizing and `layoutStruct` are untouched; `dimsTotal()` bounds the total the way the one-dimensional spelling always did, so `i32[1000][1000]` is still refused. **One chain shape** serves assignment and expression alike: the array's name rides on the innermost `Index` node and each subscript above it is another `Index`, which is why `a[i][j] = v` and `a[i][j]` reach the *same* address computation; a single subscript still comes back as itself, so the one-dimensional path is unchanged in every respect. **Sema walks the chain** (`indexChainOf`): dimension *k*'s bounds come from `dims[k]`, the answer is a row unless this is the innermost subscript, and *every* subscript in the chain is checked — an inner `a[true][0]` is as illegal as an outer one, which is the hole a per-level walk closed. **Codegen's `emitIndexAddr()` computes every subscript first and materializes the base address after**, because evaluating a subscript can materialize a global's address into X16 — where the base is about to go — and then scales each subscript by `emitElemStride` (a shift for a power-of-two stride, a 32-bit materialize plus `UMADLL` otherwise). **A chain that stops short of the elements addresses a row, and a store to a row is refused** in both assignment forms — including the single-subscript spelling, which arrives from the parser as itself and is told apart from a chain by the subscript count the parser records. **No program that compiled before changes by a byte**: 288 of 288 pre-existing baseline rows reproduce, and the chain path is only entered when a second subscript exists. New resident suite `tests/multi-dim-array-checks.sh` [9/9]: **12 behavioural cases** (every chain shape, both scopes, a struct-field grid, a 24-byte `i64` row, a 1-byte `u8` grid, and chains inside two nested `for` loops), **4 gcc-differential pairs** (the example against its C twin `tests/multi-dim-array-twin.c`, both exiting 255), a **22-row rejection matrix** (two of which pin the holes this round found in its own first draft), a **36-row coverage map**, and an **8-mutant layer** — one mutant re-creates the row-stride arithmetic, one drops the per-level check so an inner bool literal compiles, and one withdraws the row-store refusal so `a[1] = 5` is accepted.

> v0.23.30-dev gives an array **an address**: `&buf` is a `ptr`, so a `T[N]` can be handed to a function by reference instead of having to live at file scope. Until now `&` was defined for a struct lvalue and nothing else, so an array was the one thing in the language a function could not reach — every array a function touches in the shipped corpus is a global for exactly that reason. **The address was already there**, which is the whole shape of this round: a local `T[N]`'s `Binding.ty` *is* `Ty::Ptr` (the array is decayed at declaration) and `gen(Var)` already emits `ADD Xd, SP, #slot*8` for it, while a global `T[N]`'s `typeOf` answers `Ty::Ptr` and `emitGlobalAddress` materializes it. So there is **no parser change, no new instruction and no new encoding** — only the rule that lets `&` ask for an address that was always being computed. **And because a named array is decayed, "is this an array?" is a question about the length, not the type**: an `i32[4]` and a `ptr` are the same `Ty::Ptr`, so `Sema::arrayOperandOf()` answers by length in three arms — a local (`b->len`), a file-scope array (`arrayGlobals`), and a struct's array field (`arrayFieldOf()`). **One honest restriction comes with it**: `p[i]` on a `ptr` is `*(p + i*4)` and Aster has no pointer type that carries a stride, so an array whose element is not four bytes wide is *refused* rather than silently mis-scaled — `'&' on an array needs a 4-byte element type: this array's elements are i64, and a ptr indexes at 4 bytes`. > v0.23.29-dev lets a **struct field be an array**: `struct Buffers { nums: i32[4], flags: bool[3], ptrs: ptr[4], pts: Vec3[2] }`. > v0.23.28-dev opens the array's element type: **`T[N]`'s element is `T`**, whatever `T` is. > v0.23.27-dev closes **four places where Aster read an expression differently from C** — all four found by writing `docs/language-reference.md` down and checking every row in it against the binary, which is the only reason they surfaced: three of them were silent (a different answer, or a truncated value) rather than an error. **`&&` now binds tighter than `||`.** They were collected by one loop, so `a || b && c` was read `(a || b) && c` — a different answer, silently, and one `docs/language-spec.md` had been contradicting for releases. > v0.23.26-dev answers the question a pointer always asks first: **is this thing null?** Before it, a `ptr` could not be tested at all — `if (p)` was refused (a ptr is not a truthy type), `p == 0` was refused by three copies of the same "pointer comparison is not supported yet", and there was no way even to *write* a null, since `let p: ptr = 0;`, `f(0)` and `return 0;` from a `-> ptr` function were all type errors. > v0.23.25-dev teaches the control flow what every other language's does: **`if`/`while`/`for` conditions now take a comparison, a `bool` expression, or *any* integer — 0 is false, non-zero is true** — and the language finally has `true`/`false` as first-class `bool` literals. > v0.23.24-dev ships the missing half of function values: **`op(x)` — a call through a `ptr` variable**. Taking a function's address had worked since the callback-table work (the address could be stored, passed as an argument and handed to C), but every call site the compiler emitted branched through a relocated `BL`, so the address could never be *called*: there was no `BLR` in the language. Now `fp(args)` with `fp` a `ptr` variable (local, global or parameter) compiles to a `BLR X9`, and the round's showcase is the callback shape — `fn apply(op: ptr, x: i32) -> i32 { return op(x); }`. **Zero parser change**: `primary()` has always produced `Call{name}` for `Ident(`, so the whole feature is dispatch. There is no function type, hence no signature *(for a bare `ptr` — **typed** fn-pointers arrived in v0.23.37-dev)*, so **every scalar argument rides at 64-bit width** — an `i32`-declaring callee reads the low half (exactly the bits a 32-bit stage would have put there), an `i64`-declaring one reads a properly extended full register (AAPCS64 leaves a sub-64-bit argument's upper half unspecified) — and the call answers `i32`. The callee's address is materialized into **X9** after the arguments are in their registers and before SP moves: X0–X7 hold arguments, X8 is the hidden result pointer, X9–X15 hold nothing live (every temporary is parked in the frame, the stack copies touch only X16/X17), so no park/restore change is needed. > v0.23.23-dev completes the raw-memory width ladder: **`load_u16`/`store_u16` (LDRH/STRH) and `load_i64`/`store_i64` (LDR X/STR X)** join `load_u8`/`store_u8`/`load_ptr`. Why `i64` matters most: assembling a quadword through the byte pair meant eight loads, seven shifts and seven ors — and `<< 32` on an `i32` is a 32-bit shift whose count wraps, so `1 << 32` is **1** (measured, not assumed), the high word silently lost, and no comparison against the same assembled value could see it. One `load_i64` is one `LDR` and cannot be wrong that way. > v0.23.21-dev gives an ELF program its own voice: the **`write(fd, buf, len)` output primitive**. > v0.23.19-dev fixes the defect that made **a `u8` argument never arrive**: `fn g(a: u8) -> u8 { return a; }` called as `g(200)` returned **0**, and had never returned anything else — a `u8` parameter has not worked since `u8` was introduced in v0.23.2-dev. It never looked like an ABI problem, because `u8` locals, globals, array elements and struct fields were all correct, and that is what made it take a round to find: the cause is one line of encoding arithmetic. AArch64's unsigned immediate offset is **width-scaled**, so its *range* differs for every width — `LDRB`/`STRB` carry the byte offset **unscaled** in 12 bits (0..4095), `LDRH`/`STRH` scale by 2, `LDR`/`STR W` by 4 and `LDR`/`STR X` by 8. `loadStackT`/`storeStackT` shifted the byte offset left by 10 for *every* width, so for `u8` an offset past 4095 was neither rejected nor wrapped onto a neighbouring byte: bit 12 of the offset landed on **bit 22**, the one bit that separates `STRB` (`0x39000000`) from `LDRB` (`0x39400000`). Every call argument is staged in the scratch area at `4160 + callDepth*256`, which is past 4095 for *every* call, so the caller **stored** the argument by loading it and handed the callee whatever the uninitialized stack held. `u16` survived on arithmetic alone (`4160/2 == 2080` fits, and even the deepest scratch — `4160 + 14*256 + 31*8 == 7992` — is 3996 after the shift); struct fields cannot reach it (a struct is capped at 1024 bytes); locals and globals sit at small offsets. The repair is `stackOffFits()`, which decides **per width** whether an offset is expressible, and `loadStackOff`/`storeStackOff`, which stage the address through `x16` (or `x17`, when `x16` is itself the operand) when it is not. A fitting offset keeps the encoding it always had, so **no pre-existing output changes by a byte: 261/261 identical** across three modes. Covered by `tests/narrow-int-abi-checks.sh` [7/7]: a strict `-Werror` build, **15 source guards**, 2 rejections (`i64` into a `u8`/`u16` parameter), **24 qemu cases in five groups (three of them through a real cross-language link)**, 8 differential comparisons against cross-compiled C, and a **real cross-language link** — Aster's object linked against an `aarch64-linux-gnu-gcc` object — which is the only witness that the *stack layout* of a narrow argument (how far the 9th sits from the 10th) agrees with what the platform actually uses. > v0.23.18-dev fixes the wide-integer correctness holes behind the new operators, and the headline is one line: **`let x: i64 = 4294967297; return x % 7;` used to return 1 — the correct answer is 5.** Three defects stacked. (a) `exprType` reported every numeric literal as `i32`, so although a literal reaching an `i64` slot was materialized at full width (`MOVZ`+`MOVK`), the five arithmetic sites then sign-extended it *from i32* and chopped the high bits back off: `return 4294967296 / 1000;` gave 0. > v0.23.13-dev answers the question **"who checks that my `extern` matches the function I actually wrote?"** — nobody, until now. Aster is a C++17 bootstrap compiler that directly emits AArch64 machine code and ELF files. It supports:

- `build-elf`: compile source and use Aster's own linker to emit a fixed-address ELF64 `ET_EXEC`.
- `build-obj`: emit an ELF64 `ET_REL` object with function and object symbols, `.data`/`.bss`/`.rodata` sections, and `.rela.text` relocation records.
- `link-obj`: merge one or more object files, resolve function and global-variable symbols, apply `R_AARCH64_CALL26`, `R_AARCH64_ADR_PREL_PG_HI21`, and `R_AARCH64_ADD_ABS_LO12_NC` relocations, and emit `ET_EXEC`.
- `build-pie` / `link-pie`: emit a **static PIE** — an `ET_DYN` executable with no interpreter, no dynamic section, and no relocation records, whose virtual addresses equal file offsets and whose `e_entry` is a plain offset. It runs at any load base.
- `build-so`: emit a **shared object** (`ET_DYN` `.so`) with `.dynamic`, `.dynsym`, `.dynstr`, a `DT_HASH` table, and `DT_RELA`/`R_AARCH64_RELATIVE` relocations that fix up one GOT-style address slot per global; exported functions are resolvable with `dlopen`/`dlsym`.
- `build-obj --pic` / `link-so`: emit **position-independent** `ET_REL` objects and link several of them into one shared object, instead of only compiling a `.so` from a single source file.
- **Cross-`.so` imports**: an `extern fn` / `extern let` that is still undefined in the output becomes a real dynamic import -- a function through a `.plt` stub carrying an `R_AARCH64_JUMP_SLOT` relocation, a global through a `.got` slot carrying an `R_AARCH64_GLOB_DAT` relocation.
- `--soname NAME` writes `DT_SONAME` and `--needed LIB` (repeatable) writes `DT_NEEDED`, both into `.dynstr`, so the dynamic loader loads the dependency before resolving imports; `.rela.plt` is described by `DT_JMPREL`, `DT_PLTRELSZ`, `DT_PLTREL` and `DT_PLTGOT`, and binding is eager (`DT_BIND_NOW`, `DT_FLAGS = DF_BIND_NOW`).
- `--bounds-check` (since v0.23.1-dev, **off by default**) traps on an out-of-bounds array index at run time: every dynamic index into a fixed-size array is compared against the array's length and raises `BRK #1` (SIGTRAP) when it is out of range. Constant indexes are still rejected at compile time either way.
- **DWARF `.debug_line`, `.debug_info` and `.eh_frame`** (since v0.23.12-dev, v0.23.32-dev and v0.23.33-dev, **off by default**): `-g` / `--debug-line` emits one row per statement — the instruction it begins at, and the `.ast` line it came from — so a debugger can set a breakpoint by source line and turn an address back into a line. The prologue is attributed to the line that declares the function. In an object file each address is a placeholder carried by `.rela.debug_line` as `R_AARCH64_ABS64`, raised by the linker; the output is strictly additive, so `-g` cannot move a byte of `.text`. **Since v0.23.32-dev the same flag also emits `.debug_info`** — a unit per object, a subprogram per function, and a variable DIE per global, local and parameter, each with its type and, for a local or parameter, `DW_OP_fbreg(slot*8)` from a frame base of `DW_OP_breg31 + 0`; its addresses travel in `.rela.debug_info`. **Since v0.23.33-dev the flag additionally emits `.eh_frame` (and `.eh_frame_hdr`)** — one six-byte CFI table per function (`CFA = SP + 8192` one instruction in; the return address saved at `CFA − 8` by every returning body, not by the entry that exits), a CIE identical to `aarch64-linux-gnu-gcc`'s, raised through `link-obj`/`link-so` and carried in its own `PT_LOAD` under `PT_GNU_EH_FRAME`; its addresses travel in `.rela.eh_frame` as `R_AARCH64_PREL32`.
- **`include "PATH";`** (since v0.23.13-dev): another file's **declarations**, brought into this one — a body and an initializer stay in the file that owns them, so the declaration cannot drift from the definition. PATH is relative to the file that writes it (C's `#include` rule) with `--include-dir DIR` overriding; a repeat is a no-op, a cycle is an error, and a local definition supersedes an included declaration.
- **Touch input** (since v0.23.14-dev, **on-device pipeline fixed in v0.23.15-dev**): `examples/native_touch.ast` wires the `ANativeActivityCallbacks` slots — window 56/64/72 plus `onNativeWindowDestroyed` at 80, input queue 88/96 — attaches an `AInputQueue` handler to Android's main looper, and repaints a dot at the finger on every motion event. v0.23.15-dev fixes a pipeline that was structurally complete but inert on a device: the input-queue slots were wired to the wrong offsets (80/88 — offset 80 is `onNativeWindowDestroyed`, so the framework was calling a window handler as an input handler), the drain loop exited on the success code (`got == 1`; `AInputQueue_getEvent` returns **0** on success and negative only when the queue is dry), and the coordinates were read from the wrong register file (Aster has no `float` type, so `AMotionEvent_getX`/`getY` are declared `-> i32`; the NDK's `float` comes back in `s0`, but an Aster call reads `w0` — different physical register files). The fix captures the `float` with a zero-argument `lrintf` call immediately after `getX`/`getY` (argument in `s0`, `long` result in `x0`), which is the one compiler change in v0.23.15-dev: `lrint*` maps to `libm.so` in `ndkLibraryFor`. The whole capture chain is verified off-device under qemu with a real glibc (`tests/touch-coord-test.ast`, `tests/touch-checks.sh` [1/4]), and the on-device run is diagnosable through `__android_log_print` traces.
- A **source-level symbol table** (`.symtab` + `.strtab`) in every final product, so `readelf -s`, `nm` and `objdump -t` can name every source function and every global/array (see *Source-level symbol table*).
- Typed `i32` function parameters, up to eight arguments, return values, nested calls, and recursion.
- **`bool`** (since v0.22.51-dev) as a first-class type with the short-circuiting logical operators `&&` / `||` and `!`: comparisons are ordinary bool expressions, a bool is materialized with `CSET`, and `bool` is never implicitly converted to or from `i32`. `else if (c) { }` chains are sugar for `else { if (c) { } }`.
- **A standalone semantic pass** (since v0.23.0-dev): every function is type-checked over the AST — with its own scope stack and the `i32` / `ptr` / `bool` lattice — before code generation begins, so a rejected program emits nothing and a type error is reported ahead of any codegen diagnostic.
- **Run-time bounds checking** (since v0.23.1-dev, opt-in): `--bounds-check` lowers every dynamic index into a fixed-size array — a global `let buf: i32[8]`, a local `let a: i32[4]`, or an array parameter `fn f(a: i32[4])` alike — to a length comparison that traps with `BRK #1` (SIGTRAP, exit 133) when the index is out of range. Off by default, so an ordinary build emits no test at all.
- **Wider integer types** (since v0.23.2-dev): `i64`, `u8`, `u16` and `u32` sit on a single unified type lattice alongside `i32`/`ptr`/`bool`. i64 uses 64-bit registers and the 8-byte AAPCS64 argument/return ABI; `u8`/`u16` use zero-extending byte/halfword loads and stores; the unsigned types use `LO`/`LS`/`HI`/`HS` condition codes and `UDIV`; wide and narrow globals and array elements are supported. i32 code paths are unchanged and byte-identical.
- **Structs** (since v0.23.5-dev): `struct Name { field: T, … }` declares a nominal composite type; `Name { … }` builds one; `.field` reads and writes it; a struct may nest another; `ptr<S>` (reached with `&v`) is a distinct pointer-to-struct type; and a struct is copied, passed and returned **by value** under AAPCS64 — one register up to 8 bytes, a register pair up to 16, and a caller-made copy reached by address (with X8 carrying a >16-byte result) beyond that. Struct globals live in `.data`/`.bss` and may be given a constant aggregate initializer, including a nested one; since v0.23.28-dev a struct global may be an **array** (`let pts: Point[4] = Point { … };`), each element a copy of the aggregate. **Since v0.23.29-dev a field may be an array** — `struct Buffers { nums: i32[4], flags: bool[3], ptrs: ptr[4], pts: Vec3[2] }` — indexed as `b.nums[i]`, walked as `b.pts[1].a` and addressed as `&b.pts[1]`; a struct that contains one may not be built by a literal (each field takes one value, an array field needs N), so it is declared and then written element by element, and a struct `let` may now carry no initializer at all and be zero-filled. **Since v0.23.30-dev a whole array field has an address of its own** — `&b.cells` is a `ptr` — so an array field can be handed to a function by reference. **Since v0.23.31-dev a field may be multi-dimensional** — `struct Grid { cells: i32[2][3] }` — subscripted as `g.cells[i][j]`, with the field's own offset composed with both strides exactly as a named array composes them. A struct is never implicitly an integer: no arithmetic, no comparison, no truth value, and no register form — a whole struct element is read field by field, or through `&a[i]`.
- **APK v1 + v2 dual signing** (v2 since v0.23.3-dev, keys as input since v0.23.4-dev): `build-apk` emits a self-contained, installable APK signed both ways with no external toolchain — with your project's debug key by default, or with a release key you supply. v1 is the JAR/PKCS#7 signature; v2 lives in an `APK Sig Block 42` inserted before the Central Directory and protects the whole file — including bytes v1 cannot see, such as the 4 KiB alignment padding between entries. Signature algorithm `0x0103` (RSASSA-PKCS1-v1_5 + SHA2-256) is deterministic, so builds are reproducible; `X-Android-APK-Signed: 2` in `CERT.SF` makes stripping the v2 block detectable. v3 is deliberately not implemented.
- **Launcher icon and a real resource table** (since v0.23.6-dev, generalized in v0.23.7-dev): every APK carries `res/drawable-nodpi/ic_launcher.png` — a 192×192 2-bit palette PNG Aster encodes itself, transparent outside a rounded plate — and a generated `resources.arsc`. `android:icon` is written as `TYPE_REFERENCE`; a resource table is not optional here, because a resource id with no table resolves to nothing and the launcher silently falls back to the system default. Since v0.23.7-dev the table is *derived*, not hardcoded: it holds as many types and entries as the build declares, every id comes from the table's own `resId()`, and `--string NAME=VALUE` (repeatable) adds inline string resources. `android:label` is no longer a literal in the manifest — it is a reference to `string/app_name`, so the app's name exists in one place.
- **Compile-time file embedding** (since v0.23.7-dev): `@embed("path")` yields the address of a file's bytes, which the compiler reads and places in `.rodata`; `@embed_len("path")` folds to the byte count as a compile-time constant, usable as an array bound or an initializer. Relative paths resolve against the source file's own directory (C `#include` rules), `--embed-dir DIR` overrides that base, and the same path embedded twice shares one copy. This is the "put the resource in the `.so`" answer for resources *your program* reads — the framework's resources still have to go through `resources.arsc`.
- **Signature verification** (since v0.23.4-dev): `aster verify-apk <app.apk>` checks an APK end to end, and `build-apk` runs the same verifier over the APK in memory before writing it — an APK that fails its own signature check is never produced.
- `extern fn name(arg: i32) -> i32;` declarations for functions implemented in another object file.
- **External pointer-argument calls**: imported `extern fn` declarations can take `ptr` arguments and are called using the AArch64 64-bit argument registers / 8-byte stack slots; v0.22.7-dev demonstrates Bionic `strlen` and `memcmp` with pointer arguments; v0.22.8-dev adds NUL-terminated Aster string literals stored in static data; v0.22.9-dev enables Aster-to-Aster calls with pointer parameters and pointer return values; v0.22.10-dev adds mixed-signature stack-ABI regression coverage; v0.22.11-dev stores string literal bytes in a dedicated read-only `.rodata` load segment for direct `build-so` output; v0.22.12-dev adds `.rodata` to PIC `build-obj` objects consumed by `link-so`, and v0.22.13-dev adds read-only `.rodata` load segments to `link-obj` and `link-pie`.
- `ptr`/`i32` argument mismatches are diagnosed; internal Aster calls support pointer parameters and pointer return values.
- File-scope global variables (`let name: i32 = <expr>;`), stored in `.data` or `.bss`, readable and writable from functions and referencable across object files.
- Fixed-length arrays whose element type is the type written before the `[N]` (`let buf: i32[8] = 0;`), with element read/write access `buf[index]`, zero storage in `.bss` and broadcast constant initializers in `.data`. **Since v0.23.28-dev `T` is any type**: `bool[N]` (a 4-byte 0/1 slot per element), a struct `S[N]` (N copies of the constant aggregate, scaled by a multiply when the struct's size is not a power of two), and a local/global `ptr[N]` (null or an address) join the integer widths. An element is an lvalue, so `&a[i]`, `a[i].f = v` and a whole-element copy all work. Constant subscripts are bounds-checked at compile time; dynamic subscripts — into a global, a local or an array parameter — can be checked at run time with `--bounds-check` (since v0.23.1-dev, opt-in; the parameter case since v0.23.36-dev). **Since v0.23.29-dev an array may also be a struct *field*** (`nums: i32[4]` inside a `struct`), indexed as `s.nums[i]` and scaled by the same element rule; a struct containing one is declared without a literal initializer and written element by element. **Since v0.23.30-dev the whole array has an address**: `&buf` is a `ptr` in all three shapes (a local `T[N]`, a file-scope one, and a struct's array field), so an array can be passed to a `ptr` parameter and written through it instead of having to be a global — since v0.23.34-dev the answer is a strided `ptr<T>` for **any** element width (`&i64buf` is `ptr<i64>`, `p[i]` strides at 8), and a strided pointer in an untyped `ptr` slot is refused rather than mis-scaled. **Since v0.23.34-dev an array may also be a parameter** — `fn sum(a: i32[4])` decays to `ptr<i32>` and strides at the element's real width — and a function may return a `ptr<T>` handing back an array's address with its stride; only the whole array *by value* is still refused. **Since v0.23.35-dev a parameter carries its dimensions** into the body (`paramDims`), so `sizeof(a)` and `len(a)` answer from inside the function, and the `sizeof`/`len` operators answer bytes and element counts for any type or array expression (`sizeof(i32)` is 4, `sizeof(i32[4])` is 16, `len(i64[2][3])` is 6). **Since v0.23.36-dev a parameter subscript is also guarded by `--bounds-check`** — `a[i]` / `a[i] = v` trap on an out-of-range run-time index exactly like a local/global array — while a default build still moves no byte. **Since v0.23.31-dev an array may be multi-dimensional** — `T[N][M]`, `T[N][M][K]` — in every shape a one-dimensional one takes (a local, a file-scope global, a struct field): `a[i]` on a two-dimensional array is a **row**, a `ptr` to `M` elements that travels to a function exactly as `&buf` does, and `a[i][j]` is the element. The outer subscript strides by the inner length times the element size and the innermost one by the element size alone, which is the stride a one-dimensional array has always had; a chain that stops short of the elements addresses a row, and **storing to a row is refused** (`a[1] = 5` on an `i32[2][3]`) — write `a[1][j] = 5`, or take the row as a `ptr`.
- Run-time global initializers: a non-constant initializer (reading other globals, calling functions) is compiled into an internal `__aster_init` routine that runs before the user program.
- `@align(N)` alignment control on global declarations, honoured in the section's `sh_addralign`, the symbol's `st_value`, and the `.data`/`.bss` layout.

The compiler and linker do not invoke an assembler, system linker, LLVM, Clang, Gradle, D8, or the Android NDK. The linker validates ELF bounds and metadata, merges `.text`, `.data`, and `.bss` in input order, rejects duplicate global definitions, requires exactly one `_start`, and reports unresolved function and global-variable references.

## Build and test

```sh
g++ -std=c++17 -O2 -Wall -Wextra -pedantic src/aster.cpp -o aster
./tests/smoke.sh
./tests/run-on-device.sh
./tests/ci.sh            # one-command full gate (see below)
```

`src/aster.cpp` also builds clean under `-Werror`; the v0.17.0 package was verified by unpacking it into
an empty directory and building with `g++ -std=c++17 -O2 -Wall -Wextra -Wpedantic -Werror` before
running every suite below.

`tests/ci.sh` is the one-command gate that runs the whole discipline end to end and exits non-zero the
moment any stage slips: it builds `aster` with `-Werror`, runs every `*-checks.sh` / `*-structural.sh` /
`e2e-*.sh` suite as a black box (each reported PASS / SKIP / FAIL, with the e2e C-ABI suites self-skipping
on a non-AArch64 host), and finishes with an APK validation gate (`validate_apk.py` + `verify-apk`) over
the `native_render`, `icon_text_demo` and `native_touch` demos. `smoke.sh` stays the curated quick subset; `ci.sh` is the
comprehensive one. On an AArch64 runner pass `HOSTCC=aarch64-linux-gnu-gcc` to let the e2e suites run for
real.

The e2e suites execute generated AArch64 binaries. On an ARM64 device they run natively; on any other
host they run through **qemu-user**, with a cross compiler for the target-architecture test hosts:

```sh
HOSTCC=aarch64-linux-gnu-gcc ./tests/smoke.sh        # qemu-aarch64 is picked up automatically
```

`tests/run-aarch64.sh` is the transparent runner behind that: it executes an AArch64 ELF natively on
an ARM64 host and under `qemu-aarch64` (with the AArch64 sysroot when present) everywhere else, while
host binaries are passed through untouched. It disables core dumps, because qemu writes both its own
core and the guest's — hundreds of MB per run — when a guest dies from a signal, which
`tests/runtime-bounds-checks.sh` makes happen on purpose. `tests/host-toolchain-probe.sh` makes each e2e suite
**SKIP with a visible reason** when `$HOSTCC` cannot emit AArch64 ELF, so the suite still ends green on
a machine without a cross toolchain. `tests/guest-libc-alias.sh` covers one more cross-environment
detail: Aster's auto-`DT_NEEDED` emits the Android soname `libc.so`, so on a glibc host the suites
drop an AArch64 `libc.so` alias into the test directory for the guest loader — and since v0.23.15-dev
also a `libm.so` alias, because the touch capture chain's `lrintf` maps to the Android `libm.so`

## Build an Android APK (`build-apk`)

Aster can package a compiled AArch64 shared object into an installable Android
APK with **no Java/Kotlin, NDK, aapt, d8, or Gradle**. `build-apk` emits a
`NativeActivity` APK: a binary-XML `AndroidManifest.xml` (carrying an
`android.app.lib_name` meta-data, `android:icon` and `android:label` as resource
references), `res/drawable-nodpi/ic_launcher.png` and `resources.arsc` (the
binary resource table that maps those ids to their values), your
`lib/<abi>/lib<libname>.so`
(4-KiB aligned), and **v1 + v2 signatures**. Every byte is hand-encoded — there is no
subprocess and no external toolchain, and Aster does **not** transpile to
another language. Aster ships with **no signing key of its own**: which key
signs the APK is your choice.

```sh
aster keygen                                  # once per project: .aster/debug.key.pem + .aster/debug.crt.pem
aster build-apk ...                           # debug build: signed with that key

aster build-apk ... --sign-mode release \
    --keystore my-release.key.pem --cert my-release.crt.pem   # signed with yours
```

`--sign-mode release` without both options **fails** — a release build never
falls back to a generated key. Keys and certificates are read as PEM or DER
(PKCS#8 or PKCS#1 private keys, X.509 certificates), so material produced by
`openssl` or `keytool` is used as-is; `--keystore-dir` chooses where a project's
debug key lives (default: `$ASTER_KEY_DIR`, else the nearest ancestor of the
working directory holding `.git/` or `.aster/`, else the working directory).
Every APK is verified in memory before it is written, and `aster verify-apk
<app.apk>` re-checks one on disk at any time.

```sh
# One step: build-apk compiles the .ast itself (v0.22.47-dev+).
./aster build-apk examples/native_activity.ast -o nativeapp.apk \
    --package com.aster.nativeapp --libname nativeapp \
    --label "Aster Native" --min-sdk 24 --target-sdk 34 \
    --version-code 1 --version-name "1.0"
adb install -r nativeapp.apk
adb shell am start -n com.aster.nativeapp/android.app.NativeActivity
```

Compilation and packaging remain separate concerns — `build-apk` runs the very
same `build-so` pipeline internally — but the common "source → installable APK"
case no longer needs a manual `build-so` first. The `.so` stays a first-class
artifact whenever you want it (for `objdump` / `readelf` / qemu inspection):
either build it yourself and hand it to `build-apk` (the two-step form still
works unchanged), or pass `--emit-so <path>` to the one-step form:

```sh
./aster build-so examples/native_activity.ast -o libnativeapp.so   # two-step form
./aster build-apk libnativeapp.so -o nativeapp.apk --package com.aster.nativeapp ...
./aster build-apk examples/native_activity.ast -o nativeapp.apk \  # one-step form
    --package com.aster.nativeapp --emit-so libnativeapp.so ...
```

`examples/native_activity.ast` defines `ANativeActivity_onCreate`; the `extern`
NDK calls (`__android_log_print`, `ANativeActivity_finish`) resolve against the
device's `liblog`/`libandroid` at load time. See `tests/run-native-activity.md`
for device steps, signature notes, and the `tests/validate_apk.py`
self-contained verifier. `tests/apk-checks.sh` runs the full
`build-so -> build-apk -> validate` chain under `-Werror` — and since
v0.22.47-dev also the one-step `.ast -> build-apk` path, asserting the packaged
`.so` is byte-identical to the two-step build with the same `DT_SONAME`.
Since v0.23.3-dev it also runs the v2 source guards and four mutation checks;
since v0.23.4-dev every build there is signed from a generated per-project key,
and the compiler-mutation step asserts `build-apk` refuses to write an APK that
fails its own signature check. `tests/signing-checks.sh` covers the key model
itself.

For a **visible** app instead of a black screen, `examples/native_render.ast`
software-renders a gradient frame into the `NativeActivity` window (via
`ANativeWindow_lock` + `store_u8`), using **function addresses** to install the
`onNativeWindowCreated` / `onNativeWindowResized` / `onNativeWindowRedrawNeeded`
callbacks — no EGL, no float ABI. Redrawing on resize matters: the window is still
small when it is first created, so a single draw leaves black bands and stretched
stripes once the layout settles. The frame writer requests `RGBA_8888` pixels and
branches on the format the buffer actually reports (32-bit RGBA, or 2-byte RGB565
encoded with arithmetic in place of shifts), so it does not smear pixels on devices
whose windows default to 565. It can be verified by eye on a device without
`adb logcat`.

> **NDK struct offsets are load-bearing.** `examples/native_render.ast` reads and
> writes raw NDK structs, so every offset is spelled out in the source with its
> authority (the `ndk-sys` bindgen bindings, which mirror the NDK headers):
> `ANativeActivity.callbacks` is at **offset 0** (not 48 — that is `sdkVersion`,
> an `int32`; reading it as a pointer crashed the render APK on launch until
> v0.22.43-dev), `ANativeActivityCallbacks.onNativeWindowCreated` is the 8th
> function pointer (**offset 56** — note `onSaveInstanceState` sits in 3rd place,
> which is why the offset is 56 and not 48), and `ANativeWindow_Buffer.bits` is at
> **offset 16** (`width@0 height@4 stride@8 format@12 bits@16`). A wrong offset is
> invisible to every static check; only a device run exposes it.

> **`stride` counts PIXELS, not bytes.** The byte offset of pixel (x, y) is
> `(y * stride + x) * bytes_per_pixel`; the row term must be scaled too.
> `y * stride + x * 4` (the v0.22.45-dev bug) writes every row 1/bpp of the way
> down — a `stride/bpp` sawtooth with only the top quarter of the window covered,
> which is what a device screenshot after v0.22.45-dev showed. Fixed in v0.22.46-dev
> and guarded by `tests/pixel-offset-checks.sh` (source pattern + a qemu self-check
> that verifies every byte of a simulated padded framebuffer).

For an **interactive** app, `examples/native_touch.ast` (v0.23.14-dev; on-device
pipeline fixed in v0.23.15-dev) is the first one that answers input. It fills
the input-queue slots of the same callbacks struct — `onNativeWindowDestroyed`
at **offset 80** (clears the window state) and `onInputQueueCreated` /
`onInputQueueDestroyed` at **88/96**, completing the +8 cadence of the window
slots at 56/64/72 — attaches the queue to the main looper
(`AInputQueue_attachLooper` with `ALooper_forThread()`), and drains it in the
callback: `getEvent` while it returns **>= 0** (0 is success; a negative value
means the queue is dry), `preDispatchEvent` (0 = handle it now; anything else =
drop this round *without* `finishEvent`, the event will come back), then for a
motion event (`AInputEvent_getType == 1`) the action and the coordinates, and
`finishEvent` either way. Every event repaints the gradient frame with a 40×40
white square at the finger, and the pipeline narrates itself to logcat on fixed
strings so a dead run leaves evidence.

> **Aster has no `float`, so the example does not decode one — it bridges to one.**
> `AMotionEvent_getX`/`getY` return a C `float`, which arrives in **s0**; an
> Aster `extern fn … -> i32` call reads **w0** — a different physical register
> file, so v0.23.14-dev captured garbage (the fix that looked right: `s0`
> "aliases the low 32 bits of w0" is *false*, no aliasing exists). v0.23.15-dev
> captures it with a **bridge**: Aster emits no SIMD instruction of its own and
> the PLT is eagerly bound, so the `s0` a float-returning call leaves behind
> survives to the next call — and a zero-argument **`lrintf()`** issued
> immediately after `getX`/`getY` (its argument read from `s0`, its `long`
> result in `x0`, whose low 32 bits Aster reads as the `i32` return) hands back
> the exact integer. The two calls must be adjacent, with no Aster call in
> between; the compiler's one contribution is mapping `lrint*` → **libm.so**
> in `ndkLibraryFor`, without which the on-device loader would abort `dlopen`
> with "cannot locate symbol". The chain is executable here, with `strtof`
> — also a C float-returning function — standing in for `getX`:
> `tests/touch-coord-test.ast` runs nine known values (including 1042.0, 1919.5
> rounding to 1920, and -12.0) through the bridge, its `.so` is dlopened by
> `tests/touch-coord-host.c` under qemu against a real glibc, and
> `tests/touch-checks.sh` [1/4] asserts the exit code — while [4/4] breaks the
> bridge (`return lrintf();` → `return junk;`, literally the v0.23.14-dev bug)

```

Function declarations use `fn add(a: i32, b: i32) -> i32 { ... }`. Calls can pass up to eight `i32` arguments. The first eight arguments use AArch64 `w0` through `w7`; the return value uses `w0`. Each function copies its incoming arguments into local stack slots. Non-entry functions save and restore `x30` (the link register), allowing nested calls and recursion. `main` is exported as the ELF entry symbol `_start` and must have no parameters. Other functions are global `STT_FUNC` symbols.

Calls generate `R_AARCH64_CALL26` entries in `.rela.text`; the linker resolves these to functions in the same or another object. For cross-object calls, declare the expected signature with `extern fn helper(x: i32) -> i32;`. The compiler checks arity against declarations known to the current source file; the linker resolves names but does not yet validate function signatures embedded across objects.

## Data sections and global variables

A file-scope declaration `let name: i32 = <expr>;` defines a global variable. A **constant** initializer (integer literals, unary minus, and `+ - * /` over those) is folded: zero is placed in `.bss`, non-zero in `.data`. A non-constant scalar initializer is a **run-time initializer** — it is compiled into the `__aster_init` routine instead of being rejected (see *v0.16.0 additions*). Fixed-length arrays (`i32[length]`) and `@align(N)` extend the same declaration syntax. A global may be read and written from any function.

Cross-object visibility uses the extended `extern` form: `extern let name: i32;` declares a global defined in another object file. This is the only way to reference a global that is not defined in the current file.

Addressing: every global access materializes the symbol address with a **page-relative ADRP + ADD pair**, then uses a plain `LDR`/`STR` through `x16`:

```
adrp x16, name             ; R_AARCH64_ADR_PREL_PG_HI21 (275)
add  x16, x16, :lo12:name  ; R_AARCH64_ADD_ABS_LO12_NC  (277)
ldr  w0,  [x16]            ; or  str  w0,  [x16]
```

Rationale for choosing the ADRP/ADD pair over `R_AARCH64_ABS64`: it needs no data-slot indirection, produces a single instruction pair per access with no extra load, keeps `.text` independent of the absolute link address, and works identically for same-object and cross-object references. `R_AARCH64_ABS64` would require a relocated 64-bit pointer slot in `.data` (a `GOT`-style indirection) and an added dependent load. `x16` (IP0) is reserved for this and is never used for expression temporaries, so it cannot be clobbered by a live temporary; the address is always materialized immediately before the load or store.

`ET_REL` objects carry `.text`, and a `.data` section (PROGBITS, `WA`) and/or a `.bss` section (NOBITS, `WA`) when the file declares at least one global. Global variables appear in `.symtab` as `STT_OBJECT` symbols whose `st_size` is 4 for an `i32` scalar or `4 * length` for an `i32[length]` array, with `st_shndx` pointing at `.data` or `.bss`; a global that is only declared `extern` appears as an undefined `STT_OBJECT` with `st_shndx` 0.

`ET_EXEC` output places `.text` exactly where v0.13.1 did (file offset `0x1000`, virtual address `0x401000`, entry `0x401000`). When the program has data, a second `PT_LOAD` program header is added on the next page boundary with `R+W` permissions, `p_filesz` equal to the `.data` size, and `p_memsz` equal to `.data` plus `.bss`; a program whose only globals are zero-initialized gets a `p_filesz` of 0 and a non-zero `p_memsz`. Programs without globals keep the single `R+X` `PT_LOAD`; v0.17.0 appends a symbol table after the loaded image (see *Source-level symbol table*) but does not move a single loaded byte.

Shadowing: a function parameter or a local `let` may reuse a global variable's name. Inside that scope the local binding wins; when the scope ends the global is visible again. A global name must not collide with a function name in the same file.

## Compile-time file embedding (`@embed`, v0.23.7-dev)

An Aster program that wants bytes of its own — a shader, a lookup table, a font, a UI layout — previously had nowhere to put them: there was no syntax that turns an arbitrary file into an array. `@embed` closes that:

```rust
let logo: ptr = @embed("res/logo.bin");          // address of the bytes, in .rodata
let n: i32    = @embed_len("res/logo.bin");      // how many bytes there are
let copy: u8[@embed_len("res/logo.bin")] = 0;    // a compile-time constant array bound
fn main() -> i32 { return load_u8(logo + 1); }
```

- The compiler **reads the file during compilation** and emits its bytes into `.rodata`; `@embed` yields a `ptr` to them. There is no runtime file I/O and no dependency on the file existing where the program runs.
- `@embed_len` is a **compile-time constant**, not a runtime call: the parser folds it to a literal, so it is legal anywhere an integer literal is — array bounds, global initializers, case values.
- **Relative paths resolve against the source file's own directory**, the way C `#include` does, so a source file embeds its neighbours no matter where you invoke the compiler from. `--embed-dir DIR` overrides that base; an absolute path ignores both.
- **The same path embedded twice is embedded once.** Blobs are interned by resolved path, so `@embed("x")` in three functions produces one copy of the bytes.
- Errors are specific rather than generic I/O failures: a missing file names both the path you wrote and the path it resolved to, a directory and an empty file get their own messages (a zero-byte resource is almost always the wrong path), and anything over 16 MiB is refused.

Remember that `ptr` indexing is **8-byte scaled** (`p[i]` is `*(p + i*8)`), so walking embedded bytes goes `load_u8(p + i)` rather than `p[i]`.

This is the answer to "can resources just go in the `.so`?" for resources **the program itself reads**. It is not the answer for resources **the Android framework reads** — those have to be in `resources.arsc`, because `android:icon` and `android:label` are resource ids and nothing but the table can resolve them (see *Build an Android APK* below).

## Resource table (v0.23.7-dev)

`resources.arsc` is no longer a hardcoded table for one icon. It is built from a list of entries, and every id in the manifest comes from the table:

| id | type | name | value |
| --- | --- | --- | --- |
| `0x7f010000` | `drawable` | `ic_launcher` | `res/drawable-nodpi/ic_launcher.png` (a path **inside the APK**, which the framework opens) |
| `0x7f020000` | `string` | `app_name` | the value of `--label` itself — nothing to open |
| `0x7f020001` | `string` | `greeting` | `--string greeting=Hello` |
| `0x7f020002` | `string` | `app_subtitle` | `--string app_subtitle="Two words"` |

Type ids are assigned in order of first appearance, entry ids in insertion order within a type, and `android:label` names `string/app_name` — so a manifest cannot name a resource the table does not hold. `--string NAME=VALUE` is repeatable; a duplicate name, a name that is not a valid resource name, or a value with no `=` are all rejected at the command line.

### How the app name is spelled (v0.23.7-dev)

`android:label` has two legal spellings and Aster writes the one **every** consumer can read:

| spelling | what the manifest holds | who can read it |
| --- | --- | --- |
| `TYPE_STRING` — spelled out **(default)** | `android:label="Aster 图标文字"` | the framework, the launcher, and every APK viewer |
| `TYPE_REFERENCE` — a pointer into the table (what aapt emits) | `android:label="@0x7f020000"` | the framework, and viewers that open `resources.arsc` |

The reference is tidier — the name lives in exactly one place — but it is only a *promise to go open the table*. The framework keeps that promise on install, so an installed app shows its name either way; a third-party APK viewer that parses the binary manifest and stops there never opens it, and shows a **blank name** for an app that is entirely fine on the device. That asymmetry is why the default is the literal. `--label-as-reference` asks for the aapt spelling back.

Either way `string/app_name` is in the table and is what the framework reads, and either way the two have to agree: `validate_apk.py` [4d] resolves whichever spelling it finds and then fails if the table says anything else. `--label-literal` / `--label-reference` pin the check to one spelling, which is how `tests/resource-table-checks.sh` [6/6] proves the flags really change the bytes — pinned the wrong way round, both are rejected. The flag changes the manifest only: `resources.arsc` comes out byte-identical (748 B both ways in the suite).

## An app that shows an icon and text (v0.23.7-dev)

`examples/icon_text_demo.ast` is the end-to-end picture of what v0.23.7-dev can do: **one Aster program, no external toolchain, that draws a 48×48 RGBA icon and three lines of bitmap text, all of it read from bytes Aster embedded at compile time.**

```sh

It uses both halves of the release at once:

| what | how |
| --- | --- |
| the 48×48 icon | `@embed("demo_assets/icon48.bin")` — 9216 bytes of RGBA, nearest-neighbour scaled to the window, `alpha ≤ 128` skipped so the rounded corners stay transparent |

## Static PIE and shared objects

Both new modes emit `ET_DYN` images whose link-time virtual addresses equal their file offsets (link base 0). The loader adds the chosen load bias to every virtual address, so nothing in `.text` depends on where the image lands.

### `build-pie` / `link-pie` — static PIE

```sh
./aster build-pie examples/pie_global_rw.ast -o app          # one source -> static PIE
./aster build-obj examples/pie_modular_main.ast -o main.o
./aster build-obj examples/pie_modular_helper.ast -o helper.o
./aster link-pie main.o helper.o -o app                      # objects -> static PIE
```

`e_entry` is an offset from base 0 (the entry code sits at file offset `0x1000`, so `e_entry == 0x1000`); the one or two `PT_LOAD` program headers are page aligned with `p_vaddr == p_offset`; there is no `PT_INTERP` and no `PT_DYNAMIC`. The kernel maps the segments at a randomised base and jumps to `base + e_entry` — no user-space loader, no interpreter, no self-relocation. This is a static PIE rather than a dynamic executable.

Position independence without text relocations: the only addressing the compiler emits is `ADRP`+`ADD` pairs for globals and `BL` for calls, both encoded by Aster's own linker as PC-relative deltas from the link-time layout. Because the loader shifts `.text` and `.data` by the same bias, every delta stays correct, so the image contains **zero relocation records** and needs no `R_AARCH64_RELATIVE` entry. v0.16.0 wrote no section header table at all; v0.17.0 adds one so that `.text`/`.data`/`.bss` and the symbol table can be described, but it still contains **no relocation section**.

### `build-so` — shared object

```sh
./aster build-so examples/so_math.ast -o libmath.so
```

Load model: an ordinary `ld.so` load. An R+X `PT_LOAD` holds the ELF header, program headers, `.text`, `.dynsym`, `.dynstr`, `.hash`, and `.rela.dyn`; a second R+W `PT_LOAD` holds `.data`, `.got`, `.dynamic`, and `.bss`; a `PT_DYNAMIC` segment points at `.dynamic`. Every non-`extern` function is exported as a defined `STB_GLOBAL`/`STT_FUNC` `.dynsym` entry whose name lives in `.dynstr` (`DT_SYMTAB`, `DT_STRTAB`, `DT_STRSZ`, `DT_SYMENT`) and is indexed by the `DT_HASH` (SysV) table, so `dlsym` resolves it.

Relocation design: each defined global gets an 8-byte **GOT-style address slot** in `.got`, initialised to the global's link-time address and covered by an `R_AARCH64_RELATIVE` relocation in `.rela.dyn` (symbol index 0, addend = that address), published through `DT_RELA`, `DT_RELASZ`, `DT_RELAENT`, and `DT_RELACOUNT`. Shared-object code does not compute a global address with `ADRP`+`ADD`; it loads the address out of the slot (`adrp x16, <slot> ; add x16, x16, :lo12:<slot> ; ldr x16, [x16]`), so the relocation is **load bearing** — a loader that skipped `DT_RELA` would hand the code an unmapped address. `R_AARCH64_RELATIVE` was chosen over `R_AARCH64_GLOB_DAT`/`R_AARCH64_ABS64` because the object has no imports: a relative fix-up needs no dynamic symbol for its target, every loader applies it before control reaches the module, and the `DT_RELA` family is exactly the metadata a single-object, dependency-free `.so` needs.

`DT_HASH` was chosen over `DT_GNU_HASH` because the SysV table is the smaller fully specified format (`nbucket`, `nchain`, buckets, chains) with no Bloom filter and no hash-ordered symbol table; glibc, musl, and bionic all understand it, and the choice is isolated inside the `.hash` builder so a `DT_GNU_HASH` table can be added later.

Both modes share one code generator; only the global-address sequence and the surrounding ELF metadata differ, and the `ET_EXEC` path is untouched.

### `build-obj --pic` / `link-so` and cross-`.so` imports (v0.18.0)

```sh
./aster build-obj --pic examples/link_so_part_a.ast -o part_a.o
./aster build-obj --pic examples/link_so_part_b.ast -o part_b.o
./aster link-so part_a.o part_b.o -o liblinked.so --soname liblinked.so
readelf -dW liblinked.so     # SONAME liblinked.so
readelf -rW liblinked.so     # only R_AARCH64_RELATIVE: part B's references resolved locally

./aster build-so examples/so_link_lib.ast    -o libdyn.so        --soname libdyn.so
./aster build-so examples/so_link_import.ast -o libdyn-import.so --needed libdyn.so
readelf -dW libdyn-import.so # NEEDED libdyn.so, JMPREL/PLTRELSZ/PLTREL/PLTGOT, BIND_NOW
readelf -rW libdyn-import.so # .rela.plt: add/mul JUMP_SLOT   .rela.dyn: counter GLOB_DAT
```

`--pic` compiles an object the way `build-so` compiles code: every global is reached through its GOT-style slot (`__aster_gat_<name>`) and no `_start` alias is emitted, so `main` stays an ordinary function and the object can be linked into a `.so`. `link-so` merges the `.text`/`.data`/`.bss` of every input object exactly like `link-obj` and then writes a shared object instead of an executable.

An `extern fn` / `extern let` that is still undefined after the link becomes a real dynamic import:

* a **function** gets a 16-byte `.plt` stub (`ADRP x16,page(slot)` / `LDR x17,[x16,#lo12(slot)]` / `BR x17` / `NOP`) and a `.got.plt` slot holding an `R_AARCH64_JUMP_SLOT` relocation, described by `DT_JMPREL`, `DT_PLTRELSZ`, `DT_PLTREL` (`DT_RELA`) and `DT_PLTGOT`;
* an **object** gets a `.got` slot holding an `R_AARCH64_GLOB_DAT` relocation, inside the existing `DT_RELA`/`DT_RELASZ`/`DT_RELAENT` range;
* every defined global is now *also* a defined `STT_OBJECT` entry in `.dynsym` (v0.17.0 exported functions only), so a second `.so` can import it by name;
* the module records `DT_SONAME` (from `--soname`, defaulting to the output file name when the dynamic path is used) and one `DT_NEEDED` per `--needed LIB`, with all strings in `.dynstr`.

Binding is eager: the object sets `DT_BIND_NOW` and `DT_FLAGS = DF_BIND_NOW`, so the loader resolves every `R_AARCH64_JUMP_SLOT` at load time and the stub needs no lazy-resolution trampoline. glibc and Android's bionic both honour this, and bionic never supports lazy binding in the first place.

The **legacy single-source path is unchanged**: `build-so` without `--soname`, without `--needed` and without any `extern` import still emits exactly the v0.17.0 bytes (proved by `tests/regression-symtab.sh`, still 13 PASS).

## Source-level symbol table (v0.17.0)

Every **final** product — `build-elf`/`link-obj`, `build-pie`/`link-pie`, and `build-so` — now carries a non-dynamic symbol table: a `.symtab` section with a companion `.strtab`, reachable through a section header table. `readelf -s`, `nm`, and `objdump -t` can name the program's code and data instead of printing anonymous addresses. `.o` objects already had one and are unchanged.

Coverage and field values:

| product | symbol | `st_info` | `st_value` | `st_shndx` | `st_size` |
| --- | --- | --- | --- | --- | --- |
| `ET_EXEC` | each source function | `STB_GLOBAL`/`STT_FUNC` | final link address | `.text` | function size in bytes |
| `ET_EXEC` | each source global / array | `STB_GLOBAL`/`STT_OBJECT` | final link address | `.data` or `.bss` | `4`, or `4 * length` |
| static PIE | each source function | `STB_GLOBAL`/`STT_FUNC` | image offset, the same frame as `e_entry` | `.text` | function size |
| static PIE | each source global / array | `STB_GLOBAL`/`STT_OBJECT` | image offset | `.data` or `.bss` | `4`, or `4 * length` |
| shared object | each source function | `STB_GLOBAL`/`STT_FUNC` | link-time virtual address (= file offset) | `.text` | function size |
| shared object | each source global / array | `STB_GLOBAL`/`STT_OBJECT` | link-time virtual address | `.data` or `.bss` | `4`, or `4 * length` |

`.bss` is a `SHT_NOBITS` section in all three products, so its symbols have an address and a size but no file bytes. `.text` is `SHT_PROGBITS` with `SHF_ALLOC|SHF_EXECINSTR` (`AX`); `.data` is `SHT_PROGBITS` with `SHF_ALLOC|SHF_WRITE` (`WA`).

Naming rules:

- Symbols use the **source names**. The entry function is published as `main`, its source name, and the conventional ELF entry name `_start` is published next to it at the same address, because that is the name the object-file/linker contract already uses for the entry (`main` is emitted as `_start` in an `ET_REL` object). `nm a.out | grep main` and tooling that looks for `_start` both work.
- Synthetic internals are **not** published. `__aster_init`, `__aster_init_next`, and `__aster_init_end` are compiler-generated, not source-level names, so they stay out of `.symtab`. They remain in an `ET_REL` object's symbol table, and `__aster_init` remains in a shared object's `.dynsym` because `DT_INIT_ARRAY` has to name it.
- Only **file-scope** names are published: functions and global variables/arrays. Function parameters and function-local `let` bindings are not symbols — Aster has no function-local storage beyond the stack frame, and there is no DWARF.

This is a name table, not debug information: **no `.debug_*` section and no DWARF** is produced, and no line-number table. For the shared object, `.symtab` is added *in addition to* the existing `.dynsym`/`.dynstr`/`.hash`, which are byte-for-byte unchanged.

Example (`examples/symbols_demo.ast`, built with `build-elf`):

```
$ readelf -s -W symbols_demo
Symbol table '.symtab' contains 8 entries:
   Num:    Value          Size Type    Bind   Vis      Ndx Name
     0: 0000000000000000     0 NOTYPE  LOCAL  DEFAULT  UND
     1: 0000000000401000   176 FUNC    GLOBAL DEFAULT    1 _start
     2: 0000000000401000   176 FUNC    GLOBAL DEFAULT    1 main
     3: 00000000004010b0    40 FUNC    GLOBAL DEFAULT    1 bump
     4: 0000000000402000     4 OBJECT  GLOBAL DEFAULT    2 counter
     5: 0000000000402018     8 OBJECT  GLOBAL DEFAULT    3 spare
     6: 0000000000402004    16 OBJECT  GLOBAL DEFAULT    2 table
     7: 0000000000402014     4 OBJECT  GLOBAL DEFAULT    3 zeroed
```

### Where the new bytes go

The symbol table, its string table, and the section header table are **appended after the last loaded byte** of the image. Nothing that the kernel or the dynamic loader reads moves:

- the program header table is byte-identical: same `e_phoff`/`e_phentsize`/`e_phnum` and every field of every entry;
- `e_entry` is unchanged;
- every `PT_LOAD` (and, for a shared object, `PT_DYNAMIC`) keeps its `FileSiz`, `MemSiz`, `VirtAddr`, `Flags` and `Align`;
- `.text`, `.data` and `.bss` keep exactly their old bytes, and so do the shared object's `.dynsym`, `.dynstr`, `.hash`, `.rela.dyn`, `.got`, `.dynamic` and `.init_array`.

Two consequences make the change easy to audit:

- For `ET_EXEC` and the static PIE, the **whole v0.16.0 file is a byte-identical prefix** of the v0.17.0 file once the four section-table header fields are masked out. Those four fields — `e_shoff`, `e_shentsize`, `e_shnum`, `e_shstrndx` — were zero in v0.16.0 (no section header table) and are the only header bytes that differ.
- For a shared object, the file is byte-identical up to the end of its loaded segments. Only `.shstrtab` moves, because the section-name table must grow to name `.symtab`/`.strtab`; `.symtab` and `.strtab` are the only new sections.

### The redefined regression standard

Appending `.symtab`/`.strtab`/section headers necessarily changes the file bytes, so the old "whole file is byte-identical" standard no longer applies to `ET_EXEC`, static PIE, or `.so`. It is replaced by:

> For every final product, the pre-existing section contents, the program header table, the entry address, and every segment's `FileSiz`/`MemSiz`/`VirtAddr`/`Flags`/`Align` are identical to v0.16.0. The only new bytes are the sections that carry the symbol table and the section header table. `ET_REL` objects are unchanged and stay byte-for-byte identical.

`tests/regression-symtab.sh` proves exactly that, for eleven products (plain and global/array-bearing `ET_EXEC`, an `ET_EXEC` with a run-time initializer, a multi-object `link-obj` result, plain and global-bearing static PIEs, a PIE with `@align(N)`, two shared objects — one with `DT_INIT_ARRAY` — and two `ET_REL` objects). For each product it checks the header fields, compares the program header table entry by entry, compares the loaded prefix byte by byte, compares every pre-existing section's type, flags, address, size, alignment, `sh_link`/`sh_info` and contents, asserts that the only added sections are the symbol table and its string table (plus, for `ET_EXEC`/PIE, the `.text`/`.data`/`.bss` the new section table describes), asserts that the added sections start past the end of the loaded image, and asserts that no `.debug_*` section appeared. References come from the fixtures committed under `tests/baseline/v0.16.0/`, or — with `ASTER_V16_DIR` — from a real v0.16.0 compiler built from its own `src/aster.cpp`.

Two assertions in the existing suites encoded the *old* file-shape contract and were restated under the new one, without losing coverage:

- `pie-so-checks.sh` used to assert `e_shoff == 0 and e_shnum == 0` for the static PIE, standing in for "there are no relocation sections". It now asserts that the section table exists and directly that the PIE's sections are exactly `''`, `.text` (plus `.data`/`.bss` when present), `.symtab`, `.strtab`, `.shstrtab` and that no `.rela*`/`.debug*` section exists — the same guarantee, stated directly. The ADRP scan that looks for an absolute text address now uses the exact `.text` section instead of `p_filesz`, which is what it always meant.
- `linker-checks.sh` used to assert `len(file) == 0x1000 + na + nb` for a text-only multi-object link, standing in for "no stray bytes". It now asserts that the loaded image still ends exactly at `0x1000 + na + nb`, that the sections present are exactly `''`, `.text`, `.symtab`, `.strtab`, `.shstrtab` (so no `.data` appeared), that nothing extends past the section header table, and that the file ends where that table ends.

Both suites keep their PASS counts (`smoke.sh` 48, `linker-checks.sh` 10), and no check was dropped.

## Language subset

Statements: `let name: i32 = expr;`, `let name: ptr = expr;`, `let name: bool = expr;` (since v0.22.51-dev), `let name: T[LENGTH] = <const>;` (local arrays, since v0.22.49-dev; any element type `T` since v0.23.28-dev; one `[N]` per dimension, `T[N][M]`, since v0.23.31-dev), `let name: S;` (a struct local with no initializer, zero-filled, since v0.23.29-dev), `name = expr;`, `buf[index] = expr;`, `p[index] = expr;` (pointer indexing, since v0.22.49-dev), `s.f[index] = expr;` (an array *field* of a struct, since v0.23.29-dev), `a[i][j] = expr;` (a multi-dimensional element, since v0.23.31-dev — one subscript on a multi-dimensional array addresses a row and may not be stored to), `return expr;`, `if (cond) { ... }` / `if (cond) { ... } else { ... }` (`else` optional since v0.23.22-dev; it was mandatory before), `else if (cond) { ... }` chains (since v0.22.51-dev), `while (cond) { ... }`, `for (init; cond; step) { ... }` (since v0.22.50-dev — `continue` runs the step first), `break;`, and `continue;`. Each branch, loop body, and `for` header introduces a lexical scope. Expressions: decimal integer literals, hexadecimal literals `0x`/`0X` (since v0.23.22-dev), variables, function calls, array element access `buf[index]`, pointer element access `p[index]`, struct array-field element access `s.f[index]` and `s.f[i].g` (since v0.23.29-dev), multi-dimensional element access `a[i][j]` and a row `a[i]` as a `ptr` value (since v0.23.31-dev), the address of a struct lvalue `&v` → `ptr<S>`, and — since v0.23.30-dev — the address of a **whole array** `&buf` / `&gbuf` / `&s.cells` → `ptr` (only when the element type is four bytes wide, since a `ptr` indexes at `*(p + i*4)`), parentheses, unary minus, `+ - * /`. Precedence, loosest to tightest: `||` < `&&` < comparisons < `+ -` < `* /` < unary `-` / `!` (since v0.22.51-dev). Conditions take one comparison: `== != < <= > >=`, using signed 32-bit comparison semantics, **or** any `bool` expression — a `bool` variable, global, `bool`-returning call, or a `&&`/`||`/`!` combination (since v0.22.51-dev). `bool` is a separate type: there is no implicit conversion to or from `i32`, and the only bool literals are `0` and `1`. Comments are supported since v0.22.43-dev (`//` to end of line, `/* ... */` across lines); source must be ASCII.

Implementation limits: at most 500 parameter-plus-local slots per function, 16 simultaneously live expression temporaries, and 32 scalar parameters/arguments (pointer-signature Aster-to-Aster calls are not yet supported). Each function reserves an 8 KiB stack frame, including a caller-save spill area and scratch slots for nested call arguments. The compiler limits nested function calls inside argument expressions to 124 levels. Arithmetic uses 32-bit wrapping. Division by zero and signed division overflow are unchecked. Definite-return analysis is conservative and does not assume loops execute.

## Current limitations and next steps

`build-elf` and `link-obj` still emit a fixed-address Linux/AArch64 `ET_EXEC` that exits with syscall 93; `build-pie`/`link-pie` emit a static PIE and `build-so` a shared object. The linker supports `.text`, `.data`, `.bss`, and the three relocation types listed above; other section types and other relocation types are not implemented. Android NativeActivity, APK packaging/signing, runtime APIs, and self-hosting are also not implemented. Global initializers may be constant or run-time expressions, fixed-length arrays (global and, since v0.22.49-dev, local) and `@align(N)` are supported. Since v0.23.28-dev an array's element type is any type — `bool[N]`, a struct `S[N]` and a `ptr[N]` join the integer widths — and since v0.23.29-dev an array may be a **struct field** (`nums: i32[4]`), though it may not be initialized by a literal or assigned as a whole. Since v0.23.30-dev `&arr` yields a `ptr` to a whole array in all three shapes, but only when the element is four bytes wide (`i32`, `u32`, `bool`, or an `S` with `sizeof(S) == 4`), because a `ptr` indexes at `*(p + i*4)`; an `i64[N]`, `u8[N]`, `u16[N]`, `ptr[N]` or a 12-byte `S[N]` is refused rather than mis-scaled. Since v0.23.31-dev an array may be **multi-dimensional** (`T[N][M]`, `T[N][M][K]`) as a local, a global or a struct field: `a[i]` on a two-dimensional array is a row — a `ptr` to `M` elements — and `a[i][j]` the element; a row may be read, passed to a `ptr` parameter and assigned to a `ptr` variable, but **not stored to** (`a[1] = 5` is refused, because a store to a row is as meaningless as a store to the array itself), and a chain may not run past the innermost dimension (`a[0][1]` on an `i32[3]` is refused). Since v0.23.34-dev an array **may be a parameter** (`fn sum(a: i32[4])` decays to a `ptr<i32>` and strides at the element's real width) and a function may **return** a `ptr<T>` handing back an array's address with its stride — only passing the whole array *by value* is still refused. Since v0.23.35-dev a parameter's dimensions are carried into the body (`paramDims`), so `sizeof(a)` and `len(a)` answer from inside the function, and `sizeof`/`len` answer bytes and element counts for any type or array expression; a parameter subscript is now guarded under `--bounds-check` (v0.23.36-dev), `len` on a `ptr` is still refused, and C's decayed-parameter `sizeof` (the pointer's 8) is deliberately not Aster's answer (the array's 16).

- Symbol versioning (`DT_VERNEED`/`DT_VERDEF`), TLS, and `DT_RPATH`/`DT_RUNPATH` are not implemented (use `LD_LIBRARY_PATH` or an absolute `--needed` path). `PT_GNU_RELRO` is emitted; run `tests/e2e-relro.sh` on the target loader to verify runtime page protection.
- No lazy PLT binding and no `PLT0` resolver stub: binding is eager by construction (`DT_BIND_NOW`).
- Imports are resolved by name only; there is no signature cross-check between separate `.so` files. (Within one build, `include` — since v0.23.13-dev — does check, because the declaration it brings in *is* the definition's own signature; a `.so` loaded at run time has no compile-time counterpart to check against, so that half stays name-only.)
- The symbol table is a **name table only**: no `DW_TAG_variable` for a function parameter or a function-local binding is taken *from it*, and only file-scope functions and globals/arrays are named. (Since v0.23.32-dev `-g` does emit names and types for locals, parameters and globals — see *DWARF `.debug_info`* — but they are written by the debug-info encoder from the AST and the frame layout, not read out of this table; since v0.23.33-dev the same flag also emits `.eh_frame` so a debugger can walk a stack — see *DWARF `.debug_info` and `.eh_frame`*.) There is still no `DW_AT_call_frame_info`, no `DW_AT_call_file`/`DW_AT_call_line` on inlined work, and no type DIE for a function *type*.
- Cross-`.so` imports stay inside the language subset: `i32` functions with at most eight parameters, and `i32` globals or arrays.
- Touch input ships as an example (`examples/native_touch.ast`) whose `float`-capture chain, wiring, signing and linking are verified off-device (the bridge itself under qemu against a real glibc, via `tests/touch-coord-test.ast` + `tests/touch-checks.sh` [1/4][4/4]); the visible response to a real finger is observable only on an arm64 device (`tests/run-on-device.sh` territory) — the same boundary the window-rendering example ships under.
- On the development host, static PIE and shared objects are verified with `qemu-aarch64` and glibc; the *real* Android/bionic loader and the device run are exercised by `tests/run-on-device.sh`, which nanib runs on the phone. `tests/run-bionic.sh` does not exist in this release: the device suite is `run-on-device.sh`.

Next steps: symbol versioning and TLS. Debug information now covers the unit, the functions, the variables, the types and the call frame — what remains are `DW_AT_call_file`/`DW_AT_call_line` on inlined work and a type DIE for a function *type*, none of which Aster emits today.

## v0.16.0 additions

- Added fixed-length `i32` arrays: `let buf: i32[8] = <const>;`. The length follows the element type (`i32[length]`), keeping the element type next to its length and matching the existing `name: type` shape. `buf[index]` reads and writes one element; the subscript is any `i32` expression, scaled by the 4-byte element width, and the base is still materialized with the `ADRP`+`ADD` pair. Zero initializers go to `.bss`; a non-zero constant initializer is broadcast to every element in `.data`. There is **no bounds checking**. Arrays cannot be function parameters, return values, or used as a whole (`buf` without a subscript, or `buf = ...`, is rejected) — index them instead. Cross-object arrays use `extern let buf: i32[8];`. Local (stack) arrays are not implemented and are rejected with a diagnostic.
- Added run-time global initializers: a scalar global's initializer may be any expression (reading other globals, calling functions, arithmetic). Constant initializers still fold to a static value; non-constant ones are compiled into an internal `__aster_init` routine.
- Initialization model and order: the object that defines `main` places a `BL __aster_init` before the first user statement of `_start`, and `__aster_init` performs the unit's run-time assignments in **source declaration order**. Each object's routine chains through `__aster_init_next` to the next object's routine in **command-line link order** (`link-obj a.o b.o` runs `a.o`'s initializers, then `b.o`'s); the last one calls a synthesized `RET`. A static PIE has no loader that would run a `.init_array`, which is why the call is emitted explicitly in `_start`. Reading a global that a later object has not initialized yet observes zero — the compiler performs **no cross-object dependency inference**. The machinery is emitted **only** when at least one non-constant global initializer exists, so a program without run-time initializers produces the same code as v0.15.0 (verified for every v0.15.0 example in `build-elf`, `build-pie` and `build-obj`, and for the multi-object links).
- Shared objects have no `_start`, so `build-so` additionally publishes the generated routine through `DT_INIT_ARRAY`/`DT_INIT_ARRAYSZ` (with an `R_AARCH64_RELATIVE` relocation on the array); the loader runs it during `dlopen`.
- Added `@align(N)` on global declarations, e.g. `let buf: i32[8] @align(64) = 0;`. `N` must be a power of two, at most 4096; otherwise it is a compile error. Alignment is applied to the offset inside `.data`/`.bss`, the symbol's `st_value`, and the section's `sh_addralign`, and the linker aligns each input object's contribution to its section alignment so the layout survives linking.
- Added examples (`array_rw`, `array_sum`, `array_bss`, `array_index_expr`, `array_extern_main`/`array_extern_defs`, `runtime_init`, `runtime_init_order_main`/`runtime_init_order_defs`, `align_global`), the structural/diagnostic `tests/global-deep-checks.sh`, the execution suite `tests/e2e-global-deep.sh` (fixed-address, static PIE, and a `dlopen` host for the shared-object initializer), and extended `tests/run-on-device.sh`.
- The old `tests/global-checks.sh` "non-constant initializer rejected" case is replaced: a non-constant scalar initializer is now a run-time initializer and the program runs with the expected result.

## v0.19.1 GNU hash update

Shared objects now publish both SysV `DT_HASH` and GNU `DT_GNU_HASH`, including the GNU hash header, bloom filter, bucket and chain data. Keeping both tables preserves compatibility with older dynamic loaders while allowing GNU-hash-aware loaders to use the new table. The implementation bucket-sorts defined dynamic symbols, emits per-bucket chain terminators, sizes the Bloom filter to the defined-symbol set, and keeps undefined imports after the hashed range. Relocation symbol indices are now resolved by symbol name, so dynamic-symbol ordering can follow the GNU hash ABI rather than relying on fixed export/import positions. `tests/gnu-hash-checks.sh` independently verifies the hash metadata and is included in `tests/smoke.sh`. GNU RELRO is deferred until the writable segment layout can be split without accidentally making application data read-only.


### v0.19.1 GNU Hash hardening

The GNU hash table now uses multiple buckets and a sized Bloom filter. Defined dynamic symbols are sorted by `gnu_hash(name) % nbuckets`, each non-empty bucket has a correctly terminated chain, and undefined imports are placed after the hashable definitions. `R_AARCH64_JUMP_SLOT` and `R_AARCH64_GLOB_DAT` relocation symbol indices are derived from the final `.dynsym` mapping. The independent `tests/gnu-hash-checks.sh` validates bucket ordering, Bloom bits, chain values and termination, and continued SysV `DT_HASH` compatibility.

## v0.20.0 GNU RELRO hardening

Both `build-so` and `link-so` now emit a `PT_GNU_RELRO` program header. Ordinary `.data` is kept before a page-aligned boundary; `.init_array`, GOT slots, and `.dynamic` are placed after that boundary and before a page-aligned RELRO end.
